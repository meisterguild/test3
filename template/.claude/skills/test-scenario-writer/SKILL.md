# /test-scenario-writer コマンド

仕様書から**ツール非依存のテストシナリオYAML**を作成するワークフローです。

```text
仕様書（任意フォーマット: txt / md / xlsx / pdf など）
   │  Phase 1: 読み込みと要件台帳の作成
   │  Phase 2: 台帳からシナリオ抽出
   ▼
シナリオYAML（ツール非依存）  <シナリオ出力先>/<slug>.yaml   ← 人がレビューする・トレーサビリティの起点
```

シナリオを自然言語のYAMLにする理由: 仕様書の解釈と動作確認を分離し、動作確認前に人がシナリオをレビューでき、仕様書⇔確認結果の対応（`source_ref`・シナリオID）が証跡として残るため。作成したシナリオに沿った実アプリの動作確認は **test-scenario-runner スキル**が担う。

## 使い方

| 呼び出し                                                | 動作                                                    |
| ------------------------------------------------------- | ------------------------------------------------------- |
| `/test-scenario-writer <仕様書パス>`                    | 仕様書からシナリオYAMLを作成                            |
| `/test-scenario-writer <仕様書パス1> <仕様書パス2> ...` | 複数仕様書（要件定義書 + 基本設計書など）を統合して抽出 |

## Phase 0: 出力先と既存シナリオの確認

1. **出力先の決定**: シナリオYAMLは `docs/deliverables/test-scenarios/<slug>.yaml`（`<slug>` は対象システムを表す英小文字。例: `attendance`）。プロジェクトに既存の置き場の慣習があればそちらに従う
2. **既存シナリオの有無**: 出力先に対象仕様書由来のYAMLが既にあれば、仕様書が改訂されていない限り作成不要（そのまま test-scenario-runner へ案内する）。仕様書が改訂されている場合は既存IDを維持して差分のみ反映する

## Phase 1: 仕様書の読み込みと要件台帳の作成

漏れは「1回の読み取りで保持・変換する量」が増えるほど起きる（長い入力ほど中盤が抜け、要約するほど項目が落ちる）。本フェーズは**1回の仕事量を小さく保つ**ことで漏れを防ぐ。AIの成果をAIが再点検する工程は設けない。

### 1. スライスを密度で切る（1回の入力量を絞る）

抽出単位は文書構造ではなく**要件密度**で切る。目安は1スライス = 1節（`6.2` 等）または葉アイテム約30個まで。大きな文書では、このスライス単位でサブエージェントに「読み込み → 台帳化」を委譲して並列に進める（台帳は1つに統合）。1スライスが大きくなりそうなら更に細かく割る。

### 2. 列挙はコードで行う（数える作業をAIから外す）

xlsx の表・採番リストなど構造のあるソースは、まず全文をテキスト化し（下の拡張子別の表）、**スケルトン生成スクリプト**で「1行 = 1ソース単位」の連番リストを作る:

```bash
# xlsx は先に scripts/xlsx-to-text.mjs でテキスト化してから渡す。スライスごとに分けて渡してよい
node <skill>/scripts/extract-units.mjs <テキスト化済みソース>... > <シナリオ出力先>/<slug>.units.tsv
```

この連番リスト（末尾に単位総数が出る）が「数え漏れゼロ」の**機械的な分母**になる — AIが「全部で何項目あるか」を判断・列挙しない。各エージェントは自分のスライス分の units を**上から順に1単位も飛ばさず**処理する。自由記述のPDF段落など機械列挙が効かないソースは、手順1（細かいスライス）と手順3（転記専念）だけで対応する。

### 3. 転記する・判断しない（1回の変換量を絞る）

units を台帳へ写すときは、**要約せず・テスト可否を判断せず**、ソースの記述をそのまま写す:

- 表の各行・各箇条書き・各備考・**「〜の場合のみ」等の各条件節**を、それぞれ**別の1行**として転記する（複数のことを1行に圧縮しない）
- 「テスト可能か」「シナリオか `unmapped` か」はここで決めない（Phase 2 の仕事）。見出し・空行・概要文など要件でない unit だけ、台帳行の「対応」欄に `対象外` と記入して次へ進む
- 各台帳行に元の unit 連番を残す（機械照合用。`source_ref` とは別）

**網羅の確認（機械的）**: 転記が終わったら lint を実行し、未処理 unit（台帳のどの行にも出てこない連番）が無いことを確認する:

```bash
node <skill>/scripts/lint-scenarios.mjs <シナリオ出力先>/<slug>.inventory.md <シナリオ出力先>/<slug>.units.tsv
```

要件台帳 `<シナリオ出力先>/<slug>.inventory.md` の形式（1アサーション1行。「対応」欄は `対象外` のみ Phase 1、それ以外は Phase 2 で記入）:

```markdown
| No  | unit | source_ref                          | 要件（転記）                         | 対応               |
| --- | ---- | ----------------------------------- | ------------------------------------ | ------------------ |
| 1   | 0042 | 第2章 ログイン画面 > ログインボタン | 認証成功時にダッシュボードへ遷移する | （Phase 2 で記入） |
```

| 拡張子            | 読み方                                                                                                                                                   |
| ----------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `.txt` `.md` など | Read ツールで全文読む                                                                                                                                    |
| `.xlsx`           | 同梱スクリプトで全シートをテキスト化する: `node <skill>/scripts/xlsx-to-text.mjs <パス> > <出力>.txt`（セル内改行は空白に潰され 1論理行=1物理行 になる） |
| `.pdf`            | Read ツールの pages 指定で全ページ読む                                                                                                                   |
| `.docx` など      | 利用可能な変換ツールでテキスト化して読む（例: `pandoc`）                                                                                                 |

章番号の体系（`第N章` / `A-1-1` / `(1)` / `5.1.2` / シート名）は文書ごとに異なる。判別して `meta.format_notes` に記録し、`source_ref` は原文の体系で書く。

## Phase 2: シナリオ抽出 → YAML（ツール非依存形式）

**仕様書本文ではなく要件台帳を入力にして**、[references/scenario-schema.md](references/scenario-schema.md) に従い、シナリオ出力先に `<slug>.yaml` を書く（粒度の判断に迷ったときだけ仕様書の該当箇所を読み直す）。スキーマ・type/priority・抽出ルール・E2E非適要件の処分（`unmapped` の disposition）の定義はすべて scenario-schema.md が唯一の正 — **書き始める前に必ず読む**。

- **台帳の全行を消し込む**: 台帳の各行の「対応」欄に、対応するシナリオID または `unmapped` を記入する（Phase 1 で `対象外` を記入した行はそのまま）。1行も宙に浮かせない
- 1台帳行に複数アサーションが同居している行を見つけたら、シナリオ化の前に行を分割してから消し込む（1アサーションが1シナリオまたは1 unmapped に対応する状態にする）
- 特に抽出ルール4（要件定義に書かれている粒度で書く）と5（規則・数値はその規則自体を `expected` に明記し、上位概念で言い換えない）を落とさない

書き終えたら同梱スクリプトで機械検証する（プロジェクトルートで実行。YAMLパーサとして `js-yaml` または `yaml` パッケージが必要）:

```bash
# スキーマ検証（エラーは修正必須）
node <skill>/scripts/validate-scenarios.mjs <シナリオ出力先>/<slug>.yaml
# 完全性リント: 消し込み漏れ・対応欄未記入・処分矛盾・規則/数値トークンの取りこぼし・unmapped件数不一致を決定論的に検出
node <skill>/scripts/lint-scenarios.mjs <シナリオ出力先>/<slug>.yaml <シナリオ出力先>/<slug>.inventory.md <シナリオ出力先>/<slug>.units.tsv
```

lint の警告は誤検出を含むので機械的に潰さず、1件ずつ要否を判断する（警告0件なら、消し込み等式『要件行数（対象外を除く）= シナリオ対応行 + unmapped行』の成立が機械確認済み）。units.tsv の無いソース（自由記述PDF等のみの場合）は units.tsv を省略してよい。

## 完了時の報告

ユーザーへサマリを提示する:

- 台帳の消し込み結果（全N件 = シナリオ化M件 + unmapped K件、残0件であること）
- 画面別シナリオ件数、type別内訳
- `unmapped`（動作確認対象外とした要件と理由）の一覧

あわせて、YAMLを人がレビューした上で **test-scenario-runner スキル**（`/test-scenario-runner <yamlパス>`）で動作確認する流れを案内する。対象アプリが未実装の段階でも、シナリオ作成はこの時点で完了してよい（実装後に test-scenario-runner を実行する）。

## 注意事項

- 仕様書に書かれていない振る舞いを確認項目として創作しない（補完した解釈はシナリオの `notes` に明記）
- 台帳（`.inventory.md`）と units（`.units.tsv`）はシナリオYAMLと同じ場所に残す — 仕様書改訂時の差分反映と、動作確認後のトレーサビリティ確認に使う
