# テストシナリオYAML スキーマ

仕様書（任意フォーマット）から抽出したテストシナリオの中間形式。
**特定のテストフレームワーク・ツールに依存しない**自然言語ベースの記述とし、
仕様書と動作確認結果の間のトレーサビリティを担う。

検証コマンド（プロジェクトルートで実行。`<skill>` はこのスキルのディレクトリ）:

```bash
node <skill>/scripts/validate-scenarios.mjs <シナリオ出力先>/<slug>.yaml
```

## 構造

```yaml
meta:
  source: docs/勤怠管理_要件定義書.txt # 元仕様書のパス（複数可: リストでも良い）
  system: 勤怠管理システム # 対象システム名
  prefix: ATT # シナリオIDの接頭辞（システム略号、英大文字2〜5字）
  extracted_at: "2026-06-10" # 抽出日
  format_notes: 章立て形式（第N章 + 全角丸印の階層箇条書き） # 判別したフォーマットのメモ

scenarios:
  - id: ATT-LOGIN-004 # <prefix>-<画面略号>-<3桁連番>。再抽出時も維持する
    source_ref: 第2章 ログイン画面 > ログインフォーム > ログインボタン # 仕様書内の位置（章番号体系は原文に従う）
    screen: ログイン画面
    title: 認証成功時にダッシュボードへ遷移する
    type: transition # 下表参照
    priority: high # high | medium | low
    preconditions: # 前提条件（不要なら空リスト []）
      - 有効なユーザーが登録済み
    steps: # ユーザー操作（自然言語。1行1操作。セレクタ・APIなどツール固有の表現は使わない）
      - ログイン画面を開く
      - メールアドレスとパスワードを入力する
      - ログインボタンをクリックする
    expected: # 検証項目（自然言語。1行1確認ポイント）
      - ダッシュボード画面へ遷移する
    notes: "" # 曖昧な仕様・補完した解釈・データ準備の注意など

unmapped: # E2Eシナリオにしなかった要件。漏れを暗黙にしないために必須（無ければ []）
  - source_ref: 第3章 ダッシュボード画面 > 打刻パネル > 現在時刻表示
    requirement: 現在時刻を1秒ごとに更新する
    disposition: other-layer # other-layer | impl-pending | untestable（下表参照）
    layer: unit # disposition=other-layer のとき必須（unit / feature 等、どこで検証するか）
    reason: 時間依存でE2Eでは安定確認が困難。表示更新ロジックは単体テストで検証
  - source_ref: 第5章 支払い管理 > 締め処理
    requirement: 売上が2000円以上で締め日にワーカーへ支払う
    disposition: impl-pending # 原理的に検証可能だが実装が未確認/未実装
    revisit: payouts:process バッチが手動実行可能になり次第、シード投入＋実行＋画面確認でE2E化
    reason: 締めバッチが手動実行できるか未確認。動作確認（test-scenario-runner）で実装を見て最終判定する
  - source_ref: 第4章 決済 > クレジットカード決済
    requirement: 外部決済サービスで与信・売上処理を行う
    disposition: untestable # 自動テストで検証不能
    reason: 外部決済の実取引。テスト環境で実行できない（遷移・表示は別シナリオで確認）
```

## disposition（E2Eにしない理由の処分）

`unmapped` は「捨てる」ではなく「**どう扱うか**」を仕分ける。二択（scenario / 捨てる）にすると、テスト可能なものが暗黙に消える。

| disposition    | 意味                                                                                          | 追加必須フィールド           | 例                                                                |
| -------------- | --------------------------------------------------------------------------------------------- | ---------------------------- | ----------------------------------------------------------------- |
| `other-layer`  | テスト自体は可能だがE2E非適。別レイヤで検証する                                               | `layer`（unit / feature 等） | エンブレムのランク閾値判定（→ feature）、丸め・端数計算（→ unit） |
| `impl-pending` | 原理的に検証可能だが実装が未確認/未実装。実装を見る動作確認（test-scenario-runner）で最終判定 | `revisit`（再追加の契機）    | バッチ依存の締め処理・自動承認（手動実行可なら昇格）              |
| `untestable`   | 自動テストで検証不能                                                                          | （`reason` のみ）            | 実決済・実送信・外部API・運営の手作業                             |

判定の原則: **時間依存・バッチ・要データ準備を理由に `untestable` と即断しない**。手動実行やシード投入で確認できるかは実装を見ないと分からないため、これらは原則 `impl-pending` とし動作確認（test-scenario-runner）で確定する。仕様だけの判定は過剰に除外し、実装が進むと陳腐化する。

## type の分類

| type               | 対象                           | 例                                         |
| ------------------ | ------------------------------ | ------------------------------------------ |
| `display`          | 画面項目の表示・初期値         | 一覧の列、サマリーの表示、初期選択値       |
| `input-validation` | 入力チェック                   | 必須、形式、文字数、範囲                   |
| `transition`       | 画面遷移・リンク・ダウンロード | ログイン成功で遷移、CSV出力                |
| `state`            | 状態による表示・活性制御       | 未出勤時のみボタン活性、申請中のみ取消表示 |
| `error`            | エラー表示                     | 認証失敗メッセージ                         |
| `permission`       | 権限・ロールによる制御         | 管理者のみアクセス可、未認証リダイレクト   |

## priority の目安

- `high`: 主要ユーザーフロー（ログイン、登録、申請、購入など業務の幹）
- `medium`: 個別機能の正常系・主要なバリデーション
- `low`: 表示の細部、データ準備が大掛かりな表示条件

## 抽出ルール

1. **1シナリオ = 検証可能な振る舞い1つ**。同一フォームの表示項目確認は1シナリオにまとめて良い
2. 表示・遷移・バリデーション・状態制御・権限の5観点で仕様書を走査する
3. **E2E非適の要件は捨てず `unmapped` に disposition 付きで記録する**（上の表）。`untestable` と即断せず、別レイヤ可なら `other-layer`、実装依存なら `impl-pending` に仕分ける。概要・前提などテスト対象外の地の文は台帳で `対象外` 印を付けるので `unmapped` には不要
4. **要件定義に書かれている粒度で書く**。画面要素・文言・レイアウトなど詳細設計で決まる事項は、仕様書に明記されていない限り書かない（動作確認時に実装から特定する）
5. **規則・数値はアサーションとして `expected` に明記する**。要件が丸め規則・閾値・順位・件数（切り上げ/90%/30日/上位20%/最大8件 等）を含むなら、その規則自体を確認項目にする。上位概念（「評価が表示される」）で言い換えて規則を落とさない
6. 仕様が曖昧で解釈を補完した場合は `notes` に補完内容を明記する
7. 仕様書の改訂で再抽出する場合、既存YAMLの `id` を維持し、差分（追加・変更・削除）のみ反映する
