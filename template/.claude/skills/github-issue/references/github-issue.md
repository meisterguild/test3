# GitHub Issue 操作規約

## 禁止操作

以下の操作は **明示的な指示がない限り実行しない**。「issue を整理して」「issue を消して」のような曖昧な指示で勝手に実行してはならない。明示的な指示があった場合に限り、実行前に対象を読み上げてユーザーの最終確認を取る。

| 操作 | 既定 |
| --- | --- |
| `gh issue delete` | 禁止（明示指示時のみ） |
| `gh issue comment --delete` 系 | 禁止（明示指示時のみ） |
| `gh label delete` | 禁止（明示指示時のみ） |

クローズ（`gh issue close`）は禁止対象ではない。削除を求められたときは、まずクローズで足りないかを必ず確認する。

## type 体系

issue type は **branch type / PR title type と完全一致** させる（Conventional Commits 準拠）。一意なマッピングで、issue 起点でブランチを切る運用を成立させる。

| type | 用途 |
| --- | --- |
| `feat` | 機能追加・新規実装 |
| `fix` | バグ修正 |
| `docs` | ドキュメント変更（`docs/specs/` の仕様策定・変更を含む） |
| `style` | コードフォーマット・整形（挙動変更なし） |
| `refactor` | 機能変更を伴わない内部リファクタ |
| `perf` | パフォーマンス改善 |
| `test` | テストコードの追加・修正・設計（`test-design` を含む） |
| `chore` | 雑務・依存更新・ビルド設定・規約整理 |

branch 命名・PR タイトルの type prefix には issue type と同一の語彙を使う。

## テンプレート

テンプレート本文は `.claude/skills/github-issue/references/templates/<テンプレ名>.md` を参照する。**テンプレ名と type は1対1ではなく、`docs` と `test` は用途別にテンプレが分かれる**。

| テンプレ名 | label | 用途 |
| --- | --- | --- |
| `feat.md` | `type:feat` | 機能追加・新規実装 |
| `fix.md` | `type:fix` | バグ修正 |
| `spec.md` | `type:docs` | 仕様策定・変更（`docs/specs/`） |
| `docs-other.md` | `type:docs` | specs 以外の docs 変更 |
| `style.md` | `type:style` | コードフォーマット・整形 |
| `refactor.md` | `type:refactor` | 内部リファクタ |
| `perf.md` | `type:perf` | パフォーマンス改善 |
| `test-design.md` | `type:test` | テスト設計（spec から AC/R 抽出・it.todo 雛形） |
| `test-other.md` | `type:test` | テストコードの追加・修正 |
| `chore.md` | `type:chore` | 雑務・依存更新・ビルド設定・規約整理 |

テンプレ選択は SKILL の Step 1 で「ユーザー発言の語彙」「対象パス」から判定する。

## ラベル体系

ラベルがリポジトリに存在しない場合は `gh label create` での作成を提案する（自動作成はしない）。提案時は以下の色・説明を使う。

### type 系（必須・テンプレ種別と対応）

| ラベル | 用途 | 色 |
| --- | --- | --- |

| `type:fix` | バグ修正 | `d73a4a` |
| `type:docs` | ドキュメント変更（仕様策定含む） | `1d76db` |
| `type:style` | コードフォーマット・整形 | `f9d0c4` |
| `type:refactor` | 内部リファクタ | `5319e7` |
| `type:perf` | パフォーマンス改善 | `ff7619` |

| `type:chore` | 雑務・依存更新・ビルド設定 | `bfdadc` |

### priority 系（任意）

| ラベル | 用途 | 色 |
| --- | --- | --- |
| `priority:high` | 高優先度 | `b60205` |
| `priority:mid` | 中優先度 | `fbca04` |

### status 系（任意）

| ラベル | 用途 | 色 |
| --- | --- | --- |
| `status:in-progress` | 進行中 | `fef2c0` |
| `status:blocked` | ブロック中 | `e99695` |

## 標準項目

issue 作成時の assignee / milestone は、**ユーザーが明示した場合のみ設定する**。デフォルトは未指定（聞き返さない）。

## 対象 spec の必須化

`feat` / `test-design` / `fix` などで「テスト設計のみ」「実装のみ」を目的とする issue は **対象 spec の指定が必須**。エージェントは spec ファイルパスを真理ソースとして読み取り作業に着手するため、この欄が空だと「どの仕様に従えばよいか」が一意に決まらず、起点が曖昧になる。

- **必須**: 「テスト設計だけ実施する」「実装だけ進める」が明確な issue（spec はすでに別 issue / 既存 spec として存在）
- **任意**: spec + test + 実装を 1 issue にまとめる小規模なフル機能 issue。この場合は spec テンプレを使い「(本 issue で新規作成)」と明記する

## body の更新とコメントの使い分け

issue は **「現在の ask の最新スナップショット」を body に保ち、「変更の経緯」をコメントに残す** 運用を取る。両者は役割が違うので混在させない。

| アーティファクト | 役割 |
| --- | --- |
| body | この issue が **現在** 何を求めているかの最新版 |
| コメント | スコープや方針が変わった **経緯と理由** |

### body を上書きしてよいケース

本質的に「同じ ask の言い直し」に該当するもの。コメントを残しても後から読む人のノイズになるため、body を直接書き換える。

- TBD で起票したあと、内容を詳細化する（spec を埋める）
- 文言整理・誤字修正
- 章立て・構造の見直し
- 既存情報の整理（情報量自体は変えない）

### コメントで履歴を残すべきケース

後から「なぜ？」と聞かれて答えるべきもの。body 上書きだけで済ませると、後から経緯が消えて意思決定が再開できない。コメントで残しつつ、必要に応じて body も更新する。

- **スコープ拡張**: 当初の ask に項目が追加された
- **方針転換**: A 案で進めていたが B 案に変えた
- **AC の境界条件変更**: 緩める / 厳しくする
- **明示的な却下**: 議論の結果「これは敢えてやらない」と決めた

### コメントの書き方

短く、「いつ・何を・なぜ」を 1 コメントで完結させる。body にも反映している場合はその旨を明記する。

```
[2026-05-11] スコープ追加

実装中に文字数上限の見直しが必要と判明したので追加。
業界比較から再評価し、ADR-0002 を起票。
body の「変更内容」セクションに反映済み。
```

- 1 行目: 日付 + 変更の種類（追加 / 転換 / 却下 など）
- 本文: 理由を 1〜2 行で簡潔に
- 最後: body 反映の有無

### GitHub の edit history との関係

GitHub には body 編集履歴を見る機能がある（「edited」アイコンから古い版を参照可能）。ただし:

- discoverability が低く、レビュアの目に自然に入らない
- 検索できない
- 「なぜ変えたか」は記録されない

そのため、**重要な変更はコメントを優先する**。edit history は補助的な痕跡として扱う。
