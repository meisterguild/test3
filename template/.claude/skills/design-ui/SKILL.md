# /design-ui コマンド

要件定義 md をもとに、AI エージェントが Figma で UI デザインを作成するワークフローです。各工程で人間の確認（CP）を挟みながら進めます。この SKILL.md は**指揮役**（順序・CP・共通前提）で、各工程の詳細手順は `phases/` に分けています。

このリポジトリを案件ごとに複製して使う場合は、1 つの複製 ＝ 1 案件として扱います。入力はユーザーが指定した要件定義・機能仕様の資料、出力はリポジトリ内の `docs/internal/design/` です（詳細は「使い方」参照）。

## 使い方

```text
/design-ui        # ① から全工程を CP 付きで一気通貫
/design-ui 3      # 指定した工程だけ実行（例：③ワイヤーフレーム）
```

- 工程番号：**1**=着手チェック / **2**=画面整理 / **3**=ワイヤーフレーム / **4**=デザイン / **5**=FE 引き渡し
- 引数が無ければ ① から順に、各 ★CP で承認を得ながら**全工程を一気通貫**で進める。
- 引数があれば**その工程だけ**を実行する（前工程の成果物が `docs/internal/design/` に揃っている前提。無ければ不足を確認事項として出して止まる）。
- **入力**：ユーザーが指定した要件定義書・機能仕様の資料を読む。未指定なら質問して特定する。
- **出力**：デザイン成果物は `docs/internal/design/` に出力する（既定。ユーザー指定があればそれに従う）。
- **判断基準**：共通ルール `rules/` を参照する。

## 前提（全工程共通）

- 生成ルートはエージェント + Figma 直接（Figma MCP を使用）。
- 最終的な品質判断（違和感・余白感・業務妥当性）は人間が行う。AI は生成・自己レビュー・修正を担当する。
- 自己レビュー（`rules/self-review.md`）は、制作したメインのエージェントとは別に起動したレビュー用エージェントで行う。
- 推測で進めない。不明点は確認事項として出す。
- 汎用ルール（`rules/`）に案件固有の値を書き込まない。案件固有は `docs/internal/design/` に書く。

## 工程（順序と CP ゲート）

**各 ★CP（チェックポイント）で必ず人間の承認を得てから次へ進むこと。承認なしに次へ進むことは禁止。**

| 工程 | 内容                                   | 詳細手順                | ゲート                                 |
| ---- | -------------------------------------- | ----------------------- | -------------------------------------- |
| ①    | 着手チェック（Design Readiness Check） | `phases/1-readiness.md` | → **★CP1：人間 / PM 確認**             |
| ②    | 画面整理                               | `phases/2-screens.md`   | （CP なし・③ 後にまとめて確認）        |
| ③    | ワイヤーフレーム                       | `phases/3-wireframe.md` | → **★CP2：人間確認（画面構成・導線）** |
| ④    | デザイン                               | `phases/4-design.md`    | → **★CP3：人間 / FE 確認（実装品質）** |
| ⑤    | FE 引き渡し整理                        | `phases/5-handoff.md`   | （最終・引き渡し）                     |

各工程を実行するときは、対応する `phases/N-*.md` の手順に従う。

## 成果物（docs/internal/design/ の構成）

```text
docs/internal/design/
  01-readiness-check.md   着手チェック結果
  02-screen-definition.md 画面定義
  03-wireframe-spec.md    ワイヤーフレーム仕様
  04-design-spec.md       デザイン仕様
  05-review/              自己レビュー・外部レビューの結果（レビュー指摘・監査結果・修正方針）
  06-handoff.md           FE 引き渡し資料
  design-decisions.md     案件固有の判断ログ（採用/棄却理由・Human 判断・パターン化候補。必要時に作成）
```

※ `design-decisions.md` は必須成果物ではなく、案件固有の判断ログが要る場合に作る。役割は `05-review/`（レビュー指摘・監査結果・修正方針）と分ける。

## 注意事項

- 着手チェック（CP1）の承認なしに画面整理へ進まない。
- 各 CP の承認なしに次工程へ進まない。
- 仕様にない補完は「仮置き事項」として必ず明記する。
- Figma 生成が不安定な場合は、無理に進めず止まって相談する。
- **大規模な Figma 反映・既存構造の変更・デザイン化作業の前に、Human がバックアップを確保すること。**
  - バージョン履歴のチェックポイント作成、または Figma ファイル複製を行う。
  - バージョン履歴・復元・共有設定は、現時点の Figma MCP 連携では操作できない。
  - AI は「あとで復元できる」前提で作業計画を立ててはならない。
  - デザイン化は WF 正本の Main Component を直接編集せず、別ページ（例：02_Design）および複製コンポーネント（例：03_Components）で非破壊に進める。
- **Figma ページは役割ごとに分け、AI は必要に応じてページ作成を提案できるが、Human 承認前に勝手に作成しない。**
  - ページ作成前に、**ページ名・目的・必要理由・配置内容・一時/継続利用**を提示する。
  - **Human 承認後にのみ**新規ページを作成する。
  - 既存ページで足りる場合は新規ページを作らず、**Section で整理**する。
  - 作成後は**正本ページが分かる**ようにする。一時ページは放置しない。
  - `Draft` / `Final` / `New` / `Copy` など曖昧なページ名は禁止（naming-conventions の思想と一致）。役割が重複するページは禁止。
  - 推奨ページ例：00_Flow／01_Wireframe／02_Design／03_Components／Review／Archive 等。詳細は `rules/naming-conventions.md`「Page Naming」を参照。
- **影響範囲が広い反映・レビューは、原則としてチャンク（画面群）単位で進める**：機能・状態のまとまりごとに分割して適用し、各チャンクで代表画面の node-id を添えて報告・確認してから次へ進む。これにより、誤りの波及を抑え、人間がレビュー可能な単位に保つ。報告は中立表現とし、特定の役割名を書かない。
- **1ページに画面が増えた場合は、機能・役割単位の Section に整理する**：役割ごとに Section で括り、Section 名・並び順・整列状態を揃えて俯瞰性と AI 再読込性を保つ。必要に応じてグリッド等で整列し、散在配置や役割不明・重複の Section を作らない。命名は naming-conventions に準拠する。
