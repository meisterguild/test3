# Patterns（状況別デザイン解決の辞書）

「この状況ではこう作る＋なぜ」をまとめる第3層。原則（`ui-ux-principles.md` / `quality.md`）を具体的な解決に落とすための辞書。形だけ真似る事故を防ぐため、各パターンは**採用理由**と **A/B/C 確認欄**まで持つ。

> このファイルは `rules/` 配下の**汎用テンプレ**（複製されて他案件でも使う）。案件固有の値・固有名・画面名・node-id・特定データは書かない。案件固有の生データ・判断ログは案件側の成果物（`docs/internal/design/`）に残し、ここには**一般化した原理だけ**を記述する。

## 分類（育成で移動する）

| 分類            | 意味                                 |
| --------------- | ------------------------------------ |
| **Standard**    | 反復が確認でき、今後も標準として使う |
| **Conditional** | 条件付きで使う（例外条件を明記）     |
| **Legacy**      | 過去制約由来。今後は使わない         |
| **Pending**     | 判断保留（反復・裏取り待ち）         |

分類は固定でない。反復確認が取れれば Pending → Standard、陳腐化すれば Standard → Legacy に移す。移動したら**更新履歴**（日付・理由）を残す。

## 書き方の規律

- **反復 = 正 としない。** 1 案件だけの解決は「候補」であって標準ではない。
- **v0（初期）では Standard 認定しない。** 単一案件由来は原則 **Pending / Conditional** 止まり。Standard 認定は、複数案件で反復が確認できてから行う。
- **案件固有情報を入れない。** 固有名・画面名・node-id・特定データは書かず、一般化した原理で書く（例：「特定の対象は削除不可」ではなく「参照整合が壊れる対象は削除導線を出さない／確認する」）。
- **形だけでなく採用理由（Why）を書く。** なぜその解決が良いか・どんなリスクを防ぐかまで残す。
- **A/B/C 確認欄を持たせる。** Pattern 化しても全部を A（機械チェック）にしない：**存在・最低条件＝A、妥当性・美的判断＝B/C** に残す（`self-review.md` の役割分担・A/B/C 分類と揃える）。
- **棄却案が無いときは空欄にしない。** 「未記録。次回以降、代替案の比較検討または Human 判断で棄却案が出たら追記する」と明記する（書き忘れか材料無しかを区別するため）。

## パターン書式

各パターンは次の項目で記述する。

```text
### PT-XXX-NN: <パターン名>
- 状況: いつ・どの文脈で使うか（適用条件）
- 推奨: こう作る
- 避ける: こうしない（アンチパターン）
- 採用理由: なぜ良いか・何を防ぐか
- 例外条件: この条件では推奨が変わる（Conditional の根拠）
- 分類: Standard / Conditional / Legacy / Pending
- 出典・確度: 何を根拠にしたか・反復件数
- 棄却した代替案と理由: 検討して外した案（次回の判断材料。無ければ空）
- 確認の割り当て:
  - A（Self Review）: 存在・最低条件として機械確認できること
  - B（Independent Review）: 妥当性・案比較で見ること
  - C（Human）: 業務・ブランド・美で最終判断すること
```

## 削除（Delete）

### PT-DEL-01: 破壊的操作（削除）の起点と確認

- 状況: 一覧／詳細でデータを削除できる画面
- 推奨: 削除の**起点を明示的に置き**（一覧の項目メニュー、または詳細画面内）、実行前に**確認を挟む**。確認は「タイトル（体言止め）＋影響の明示＋[キャンセル]／[削除]」。削除の見た目は**控えめ**にする。
- 避ける: 起点の無い確認ダイアログ（到達不能）／確認なしの即削除／削除を主操作級に強調する
- 採用理由: 削除は低頻度・高リスク。**起点の存在**（到達できること）と**確認**（誤操作防止）が最低条件。強調しすぎると誤操作を誘発するため、控えめが定石。
- 例外条件: 他データから参照される対象（マスタ等）で参照整合が壊れる場合は、「削除不可」または「無効化で代替」が仕様上妥当なことがある → **可否は仕様／PM 判断**（デザイン側で決めない）。
- 分類: **Conditional / Pending**（単一案件由来・反復未確認。v0 では Standard にしない）
- 出典・確度: 初出案件の判断ログを一般化（削除の起点欠落を修正／削除可否は確認事項として分離）。反復 1 件。
- 棄却した代替案と理由:
  - 未記録。次回以降、代替案の比較検討または Human 判断で棄却案が出たら追記する。
- 確認の割り当て:
  - A（Self Review）: 削除操作に**起点 UI と到達経路**があるか（`self-review.md`「操作 ↔ UI 入口の照合」）／確認ステップの有無
  - B（Independent Review）: 起点の**配置・目立たせ方・主副の序列**が妥当か／確認文言の分かりやすさ
  - C（Human）: この対象を**削除可能にしてよいか**の業務判断／全体トーン

## 必須（Required）

### PT-REQ-01: 必須項目の明示

- 状況: 入力フォームで必須と任意が混在する画面
- 推奨: 必須をラベル横に**明示**する（「※必須」やバッジ等）。任意との区別を画面間で一貫させる。入力エラーは該当入力の**直下にインライン**で示す。
- 避ける: 必須／任意の区別なし／色だけで必須を示す／エラーをダイアログだけで示して場所が伝わらない
- 採用理由: 入力前に必須が分かると手戻りが減る。色だけの区別は色覚差・グレースケール環境で伝わらない（`quality.md`「色だけで状態を判断させない」）。
- 例外条件: 全項目が必須なら個別バッジは冗長になるため「すべて必須」と一括表示でよい
- 分類: **Conditional / Pending**（単一案件由来・反復未確認。v0 では Standard にしない）
- 出典・確度: 初出案件の判断ログを一般化（必須の明示・エラーの直下表示）。反復 1 件。
- 棄却した代替案と理由:
  - 未記録。次回以降、代替案の比較検討または Human 判断で棄却案が出たら追記する。
- 確認の割り当て:
  - A（Self Review）: 必須項目に必須表示があるか（有無）／入力エラーが該当入力の近くにあるか
  - B（Independent Review）: 必須表現の分かりやすさ・一貫性／必須の多寡に応じた見せ方
  - C（Human）: 必須表示の文言・トーン

## エラー（Error）

### PT-ERR-01: エラーの表示位置と伝え方

- 状況: 入力エラー・処理エラーを表示する画面
- 推奨: 入力エラーは該当入力の**直下にインライン**で、何をどう直せばよいか分かる文言にする。補助情報（エラーコード等）は主メッセージの下に小さく添える。状態色（赤）は**最小適用**にし、色以外（文言・アイコン）でも意味が伝わるようにする。
- 避ける: エラーをダイアログだけで示して場所が分からない／画面全体・大きな面を赤で塗る／色だけで判断させる
- 採用理由: 直したい箇所の近くにエラーがあると修正が速い。色の過剰適用は情報の優先順位を崩し、色依存は色覚差で伝わらない（`ui-ux-principles.md`「状態・フィードバック」）。
- 例外条件: フォーム外の致命的エラー（通信断・取得失敗など）は、ページレベルの通知や別画面での復帰導線が妥当なことがある
- 分類: **Conditional / Pending**（単一案件由来・反復未確認。v0 では Standard にしない）
- 出典・確度: 初出案件の判断ログを一般化（エラーの直下表示・状態色の最小適用・色以外での伝達）。反復 1 件。
- 棄却した代替案と理由:
  - 未記録。次回以降、代替案の比較検討または Human 判断で棄却案が出たら追記する。
- 確認の割り当て:
  - A（Self Review）: エラー状態の有無／入力エラーが該当入力の近くにあるか／状態色が最小適用か（大面積塗りでないか）
  - B（Independent Review）: 文言の分かりやすさ・復帰導線の妥当性
  - C（Human）: 業務的な言い回し・トーン

## 空状態（Empty State）

### PT-EMPTY-01: 空状態・未取得値の見せ方

- 状況: データ 0 件の一覧、または任意項目・取得値が未設定／null の表示
- 推奨: 一覧の空は「何が無いか＋（あれば）次アクション」を示す**空状態表示**にする。項目単位の null／未取得は「—」「未取得」等の**代替表示**で空欄放置しない。ReadOnly 項目の未取得も明示する（空欄で誤解させない）。
- 避ける: 0 件で真っ白／null を空欄放置で「不具合か未取得か」が不明／情報欠落を隠す
- 採用理由: 空・未取得を明示すると「壊れている？」の誤解を防げる。次アクション提示で離脱を防ぐ。
- 例外条件: 表示要否・代替表示の文言、null 時に「行非表示」か「— 表示」かは**仕様／PM 判断**（デザイン側で決めない）
- 分類: **Conditional / Pending**（単一案件由来・反復未確認。v0 では Standard にしない）
- 出典・確度: 初出案件の判断ログを一般化（未取得値の代替表示・空状態の明示）。反復 1 件。
- 棄却した代替案と理由:
  - 未記録。次回以降、代替案の比較検討または Human 判断で棄却案が出たら追記する。
- 確認の割り当て:
  - A（Self Review）: 空状態表示の有無／null・未取得時に代替表示があるか（空欄放置でないか）
  - B（Independent Review）: 空状態メッセージ・次アクションの妥当性
  - C（Human）: 表示要否そのもの（業務判断）・文言

## モーダル（Modal / Dialog）

### PT-MODAL-01: ダイアログの構成と揃え

- 状況: 確認・告知・入力をモーダル／ダイアログで出す画面
- 推奨: 「**タイトル（体言止め）＋内容＋アクション**」で統一する。1 文で完結する確認でもタイトルを省略しない。揃えは中身で使い分ける＝**メッセージ型はセンター揃え／フォーム型は左揃え**（ラベルは必ず左揃え）。本文は**文節（意味のまとまり）で改行**。補助情報は下に小さく。画面に対し**垂直中央**に配置する（固定座標でなく中央計算）。
- 避ける: タイトル省略／語尾のばらつき（〜です・〜ますの混在）／フォームの中央寄せでラベルと入力の対応が崩れる／固定座標配置で高さ変化に追従しない
- 採用理由: 構成統一で用件把握・読み上げが安定する。揃えの使い分けで可読性を保つ。中央計算で画面・モーダルの高さ変化に強い。
- 例外条件: タイトルの体言止めの具体表現・文言の厳密さ・トーンは案件で調整する
- 分類: **Conditional / Pending**（単一案件由来・反復未確認。v0 では Standard にしない）
- 出典・確度: 初出案件の判断ログを一般化（構成統一・揃えの使い分け・改行・垂直中央）。反復 1 件。
- 棄却した代替案と理由:
  - 未記録。次回以降、代替案の比較検討または Human 判断で棄却案が出たら追記する。
- 確認の割り当て:
  - A（Self Review）: タイトル／内容／アクションの 3 構成があるか／フォーム型でラベルが左揃えか／垂直中央に配置されているか
  - B（Independent Review）: 揃えの使い分けの妥当性・改行位置の読みやすさ
  - C（Human）: 文言・トーンの最終判断

## 更新履歴

- v0: 初期作成。分類定義・書き方の規律・パターン書式・初期カテゴリ（削除・必須・エラー・空状態・モーダル）を用意。削除カテゴリを Pending / Conditional 候補として記述（Standard 認定なし）。
- v0（追記）: 必須・エラー・空状態・モーダルの 4 カテゴリを、判断ログを一般化した Pending / Conditional 候補として追加（PT-REQ-01 / PT-ERR-01 / PT-EMPTY-01 / PT-MODAL-01）。棄却案が無い場合は「未記録」明記の運用を規律に追加。すべて Standard 認定なし・案件固有情報なし。
