# UI/UX 原則（操作性・最小セット）

操作性・使いやすさの普遍原則を要点だけまとめる。網羅は目指さず、効果が高いものに絞る。案件固有のルールは書かない（案件側 docs/internal/design に書く）。

> 視覚品質・アクセシビリティは quality.md、WF の作り方は wireframe.md を参照（重複は最小限）。

## 操作・タップ

- タップ領域は十分に確保する（目安 48×48px 以上）。小さすぎる操作要素を避ける。
- ボタン・入力（テキストボックス／ドロップダウン）・選択コントロールの**高さは役割ごとに統一**する（同じ役割の要素に、説明できない高さ違いを作らない）。サイズを変えるのは役割が異なるときだけ。
- 二択・少数の択一は、押しやすいセグメント／十分な大きさにする（小さいピルを避ける。特にモバイル）。
- 主要操作（CTA）の位置を画面間で統一する（例：主要操作・追加は下部に固定）。
- 選択コントロールは選択中を 1 つ塗って「選べるボタン群」だと分かるようにする。
- 操作できない要素は、**押せない理由と復帰条件**を示す（disabled で放置しない）。原因（権限不足／状態不一致／入力不足／業務ルール）に応じて、非表示・無効＋理由・説明付きエラーを使い分ける（可否の内容自体は仕様に従う）。

## 入力

- 必須項目を明示する（「※必須」など）。任意との区別を明確に。
- 入力エラーは**該当入力の近く（直下など）**に出し、何をどう直せばよいか分かる文言にする。ダイアログだけで済ませると場所が伝わらない。
- 入力負担を減らす：必要な項目に絞り、すでにある情報は再入力させない（既定値・前回値・自動補完）。ただし自動補完・既定値の取得元/可否は仕様に従う（無ければ確認事項）。
- ユーザーが詰まりやすい箇所（専門用語・複雑な入力・エラー）には、入力例・用語説明・問い合わせ先などの解決導線を添える（何を出すか・要否は利用者/頻度に依存）。
- 確認・破壊的操作（削除など）は確認を挟む。

## 重要操作の事前明示

- 影響の大きい操作（課金・送信・申請・削除・重要な設定変更）は、実行前に「何が起きるか」を画面上で先に示す（後出しにしない）：**影響範囲・条件・通知先・反映タイミング・変更/取消可否**。
- ただし通知先・反映タイミング・変更/取消の可否などの業務挙動は仕様で決まる。仕様に無ければ勝手に決めず確認事項に出す（**PM/仕様確認**）。WF では「その情報を出す枠」を確保する。
- 設定変更・マスタ編集・金額/申請内容の変更など重要な変更は、確定前に「何が・どう変わるか（**変更前→変更後**）と影響範囲」を示す。差分として何を見せるべきかの業務重要度は仕様/PM に従う。

## 取り消し・キャンセル・復元

- キャンセル／戻る／取り消し（undo）／復元を区別して扱う：キャンセル・戻るで未保存入力が破棄される場合は確認を出す。削除・変更の取り消し（undo）や削除後の復元の可否・取消可能時間は仕様に従う（無ければ確認事項）。

## ダイアログ・モーダル

- 基本構成は **タイトル＋内容＋アクション** で統一する。タイトルは「一目で何のモーダルか」が分かる短い見出しにする（用件の把握・読み上げの起点になる）。内容が1文で完結する確認でもタイトルを省略しないのを既定とする。
- タイトルは**体言止めの短い見出しで統一**する（語尾「〜です／〜ます」のばらつきを避ける。一覧の統一感が増し、1行に収めやすい）。
- 揃え方は中身で使い分ける。
  - **内容がテキストのみ（確認・告知などメッセージ型）** → タイトルと本文を**センター揃え**。
  - **フォーム（ラベル＋入力枠を含む）** → タイトルも含め**左揃え**。特にラベルは必ず左揃え（ラベルと入力枠の対応・視線の起点を保つ。中央寄せは可読性を損なう）。
- 本文や状態メッセージ・トースト等の**メッセージ系テキストは、変な位置で折れないよう文節（意味のまとまり）で改行**する（短い文は原則調整。長文・レイアウト制約で不可の場合は除く）。
- 補助情報（エラーコード等）は主メッセージの下に小さく添える。
- 画面に対する配置は**垂直方向の中央**を基本とする（固定座標ではなく中央計算で置き、画面やモーダルの高さが変わっても中央を保つ）。

## 状態・フィードバック

- 空・読み込み中・成功・エラーの各状態を必ず用意する（詳細は wireframe.md / quality.md）。
- ローディング / 処理中は「読み込み中」で終えず、処理内容が分かる文言にする。待ち時間が長い・失敗リスクがある・ユーザーが不安になりやすい処理では、可能な範囲で待ち時間の目安や次に起きることを伝える。
- 操作の完了は明確にフィードバックする（トースト等）。
- **状態色は最小適用にする**：危険・警告・成功などの状態色は、画面全体や大きな面を過剰に染めず、意味を伝えるのに必要な箇所（見出し・小アイコン・該当要素の枠 等）に**限定**して使う。面全体を強い色で塗ると情報の優先順位が崩れる。
- **色に頼りきらない**：色は補助とし、文言・ラベル・レイアウト・アイコンでも意味が伝わるようにする（「色だけで状態を判断させない」の詳細は `quality.md`）。Error / Warning / Success 等の意味は画面間で一貫させる（色の割り当ては `tokens-and-scales` の Role、一貫は「一貫性」節）。

## 一貫性

- 同じ意味の要素は、同じ見た目・同じ位置にする。
- 色の意味を統一する（例：危険・エラー＝赤）。

## 言葉・順序

- UI 上の文言・項目名・操作名は、DB 名・開発者用語・内部処理名をそのまま使わず、ユーザーが業務で理解している言葉に置き換える。置き換え判断が必要な場合は PM/業務担当に確認する。
- 画面や入力の順番は、システム内部の処理順ではなく、ユーザーの業務手順・判断順に沿わせる。業務順序が不明な場合は確認事項に分離する。

## 認識しやすさ

- ユーザーに前画面の内容・入力形式・選択条件を覚えさせない。選択済み条件、現在位置、入力例、候補、前回値、処理対象を画面上で確認できるようにする。
- アイコンだけ、抽象的なメニュー名、開かないと意味が分からない操作を避ける。必要に応じてラベルや補足文を添える。

## 効率化

- 利用頻度が高い業務・繰り返し作業では、毎回同じ手順を踏ませない。前回値、保存済み条件、テンプレート、一括操作、よく使う操作への近道を検討する。
- キーボードショートカット等の詳細操作は実装・プロダクト方針に依存するため、WF では必要性の確認に留め、仕様未定なら確認事項に分離する。
