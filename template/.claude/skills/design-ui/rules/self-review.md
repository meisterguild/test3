# Self Review（自己レビュー観点）

生成した Figma 成果物を人間へ見せる前に監査するためのファイル。監査は、制作したメインのエージェントから独立して起動する**レビュー用エージェント（サブエージェント）**が実施する。制作時の文脈・思い込みを持ち込まず、成果物と仕様だけを根拠に判定するためで、メインのエージェント自身による読み直しでは代替しない。**生成（メイン）→ 別エージェントで監査 → 修正（メイン）→ 再監査（別エージェント）→ 人間レビュー**、の順で使う。

役割分担：

- **レビュー用エージェント（メインとは別に起動）が見る**：構造・命名・Component・状態・トークン整合など「機械的に判定できること」。修正はせず、監査レポートを返す
- **メインのエージェントが行う**：監査レポートに基づく修正と、再監査の依頼
- **人間が見る**：UX 品質・ブランド品質・違和感・情報の優先順位（このファイルの対象外。人間レビューで扱う）

## レビューの回し方（自己レビューでの具体運用）

確認の一般原則（Critical 0 件 ＋ 観点を変えて 2 回確認。`design-readiness-check.md`「質問の分類と終了条件」と共通）を、この自己レビューでは次のように具体化する。

- Critical が 0 件になるまで「修正 → 再監査」を繰り返す。
- 0 件になったら、**観点を変えて 2 回**確認して終了する（**1 回目＝画面・状態・遷移起点／2 回目＝表示データ・取得元・データ要件起点**）。同じ読み直しの反復ではなく、違う角度で見落としを拾うのが目的。
- Warning / Review は残ってよい（影響・対応方針・判断先を明記する）。
- **指摘・想定は実データで裏取りしてから直す**：レビュー指摘や自分の想定を鵜呑みにせず、Figma の実データ（ノードの実値）や仕様で確認してから修正する。「既に正しい」「別の箇所が原因」ということがあるため、思い込みでの修正を避ける。

## チェック観点（重要度別）

### Critical（必ず修正）

- 禁止レイヤー名（`Frame` / `Group` / `Rectangle` / `Wrapper` / `Copy` / `Temp` / `Final` 等）が残っている
- Property 名・Layer 名に日本語が混在している
- Detach された Instance がある
- 指定外の Icon（案件で指定した Icon Library 以外・独自生成 Icon。既定は Material Symbols）が使われている
- 表示文言そのものが Layer 名になっている

### Warning（修正推奨）

- 責務が説明できない Layer がある
- Prefix（`Txt/` `Img/` `Btn/` 等）が付いていない
- トークン（Color / Spacing / Type）を使わずベタ値が入っている
- Fixed Width / Height 依存になっている
- Auto Layout の責務が不明
- Component 化すべき繰り返し要素が Component になっていない

### Review（人間判断に回す）

- Brand Icon の採否
- 特殊な UI 表現
- デザイン品質そのもの

## 画面・内容の充足チェック

- 主要画面が揃っているか
- 権限差分（管理者／一般など）が反映されているか
- 状態・エラー（空・読み込み中・エラー・成功）があるか
- モーダルが必要箇所にあるか
- 追加 / 編集 / 削除などの CRUD 画面が、注記で済ませず**実体**として揃っているか
- 状態・エラーは**該当画面の文脈**で示しているか（別ボードへの一覧化だけで済ませていないか）
- **状態カテゴリ**（①展開 ②取得中・エラー ③空・任意未入力 ④通知・トースト・バナー ⑤OS 委譲は画面化しない）で各画面の状態が網羅されているか（`wireframe.md`「網羅性」参照）
- **1 画面が内部に複数の進行状態を持つ場合**（測定中・通信中・処理中など）は、仕様の処理ルール・例外・エラーから状態を洗い出す：通常進行／操作待ち／一時エラー（復帰可能）／終了エラー／各状態の**次画面への遷移条件**。「1 画面のメッセージ差し替えで表す」か「状態別に分けて描く」かを決めた上で、状態の抜けを作らない
- 仕様にない補完を「仮置き」として明記しているか
- 画面下部が見切れていないか
- **表示要素の増減チェック（WF ↔ 成果物）**：WF / 仕様に**ない**表示要素（アイコン・イラスト・CTA・項目 等）を追加していないか／WF / 仕様に**ある**表示要素・状態を削除していないか、を1画面ずつ突合する。追加・削除の要否は AI で確定せず「仮置き＋確認事項」として分離する。

## 操作 ↔ UI 入口の照合（CRUD Trigger Check）

仕様上の各操作に、それを起動する UI 入口（トリガー）が画面上に存在し、到達可能かを照合する。「操作の結果画面（確認ダイアログ・入力フォーム）はあるのに、そこへ行く起点が無い」抜けを防ぐ（結果画面の有無は「画面・内容の充足チェック」、ここは起点と到達経路を見る）。③WF・④Design の両方で実行する（WF では起点と遷移の存在、Design ではその維持を確認）。

この項目が判定するのは A（事実照合）だけ：入口が「在るか無いか」「どの画面に在るか」「到達経路が繋がっているか」は、別々に確認しても同じ答えになる。入口が存在する画面・場所は記録するが、その配置が妥当か、見つけやすいか、どれだけ目立たせるべきか、主副の序列が適切かは判定対象外とし、Independent Review（B）／Human（C）へ回す。「その操作を許すべきか」の可否も仕様に従い、記載が無ければ推測で入口を足さず確認事項へ分離する（no-add 原則）。

手順：

1. 仕様から操作一覧を作る：対象データ（エンティティ）× 操作。仕様に存在する操作だけを対象にする（推測で操作を足さない）。少なくとも次を漏らさない：
   - 作成 / 参照（一覧・詳細確認）/ 更新（状態変更を含む）/ 削除
   - 検索 / 絞り込み / 並べ替え / 出力 / 取り込み / 一括操作
   - フォーム・ダイアログ内の 保存 / キャンセル / 戻る（完了・離脱の入口）
2. 各操作を 1 行ずつ照合する：
   - 入口の有無：起動する UI 要素（ボタン / メニュー項目 / スワイプ / 長押し / リンク 等）が画面上に存在するか
   - 入口の場所：どの画面のどこか（画面 ID / node-id）
   - 到達経路：その画面へ他画面から遷移経路が繋がっているか（孤立画面でないか）＝経路の有無のみを見る（見つけやすさの良し悪しは B）
   - 結果画面との対応：入口 →（確認 / フォーム / 結果）の遷移先が揃っているか。片側だけ（起点の無い確認ダイアログ／押しても遷移先の無いボタン）を検出する
3. 欠けの扱い：
   - 仕様上その操作が「可能」なのに入口が無い → Critical。監査レポートの Fix Recommendation に回す（起点の追加を修正方針として明記）
   - 仕様に可否の記載が無い → 推測で入口を足さず Human/PM 確認事項へ分離（`docs/internal/design` の案件出力に記録）
   - 仕様上「不可」で入口が無い → 正しい（違反ではない）。可否の根拠を明記する

出力：操作↔入口のマトリクスを監査レポート（`docs/internal/design/05-review`）に含める。

## 表示データと実データの対応（重要）

画面の**表示ラベルだけで判断せず**、各ラベルが「どの実データ項目」を指すかを 1 つずつ突合する。ズレ・曖昧なまま進めない。特に混同しやすい：**名称／ID／コード／番号／シリアル／アドレス／機器名／位置情報／ステータス**。

各表示項目で確認：

- 実データ項目は何か（どのフィールド／値か）
- 取得元の区別（自動取得／手入力／設定値／外部連携値）
- 未取得・未設定・null のときの表示（空欄でよいか／代替表示か）
- 一覧・詳細・結果など**画面ごとの表示有無**

※ 仕様書・画面・データ項目の記載から**突合できる範囲で確認**し、対応が読み取れない場合は推測で補完せず Human/PM 確認事項に分離する。表示要否そのものの判断（例：位置情報を出すか）も、仕様に明記が無ければ勝手に決めず Human/PM 確認事項として分離する（`docs/internal/design` の案件出力に記録）。

## データ要件から UI 要件の逆算（重要）

画面起点だけでなく、**データ要件（保存項目・取得項目）起点でも走査**する。データ項目 1 つずつで確認：

- どこで作られる／入力される／保存される／表示されるか
- どの状態・設定で非表示になるか
- 削除・履歴に影響するか
- 未登録・未取得・null のときの表示

特に「**保存されるが、どの画面に表示するか／表示しない前提かが定義されていない項目**」がないか確認する（保存データは内部処理・ログ・監査用で画面表示しない場合もある。表示要否が未定なら Human/PM 確認へ）。

## 一括変更後の整合性チェック（重要）

コンポーネント置換・サイズ統一・セクション再配置など、**一括で複数要素を変えたら、人間に見せる前に必ず全体を再検証する**（変更は連鎖して別箇所を壊すため。「正常に見えても別箇所が崩れている」ことが多い）。

- **重なり**：ページ直下の各セクションを y 順に並べ、`前の下端 > 次の上端` が無いか確認する。高さを変えたら、その下の要素・**最下部の部品セクションまで**含めて再配置する。
- **潰れ・はみ出し**：固定高さのコントロール（セグメント等）のコンテナは固定高さにする／自動高さ（hug）のコンテナの子を FILL にして循環で潰さない。インスタンスが「親より広い／極端に狭い／想定外の高さ」になっていないか機械チェックする。
- **オーバーレイの追従**：画面高を変えたら、暗幕（Scrim）を画面高に合わせ、モーダル／ダイアログを再センタリングし、キャプションを画面の下へ再配置する。
- **目視**：俯瞰だけでなく、主要画面を高解像度で 1 枚ずつ確認する（小さな潰れは俯瞰で見落とす）。

## 構造チェック（structure.md と対応）

- Auto Layout になっているか／不要 Wrapper がないか
- Layer 名が適切か（naming-conventions.md）
- レスポンシブが破綻していないか
- Component / Variant / Property / Variable / Style が整理されているか

## 視覚品質ガードレールチェック（quality.md と対応）

A として確認できる範囲に限定する。余白感・密度感・美的判断（気持ちよさ・ちょうどよさ）は対象外＝B/C。

- Spacing が定義済みスケールを使っているか（直値でない）
- 余白の大きな逆転・不自然な揺れがないか（コンポーネント内 Padding・カード内余白など役割上の例外は B/C）
- タイポ階層が 3〜4 段以内か
- Primary 相当の主操作が乱立していないか
- 強調色・太字・カード・罫線が過剰に使われていないか
- 同一列の端の不揃い／同一役割要素の幅・高さの不揃い／小数点座標／はみ出しがないか

## 監査レポートの形式

自己レビュー結果は次の構成で出力する（`docs/internal/design/05-review` に保存）。

- Audit Summary（概要）
- Critical Issues（必ず修正）
- Warning Issues（修正推奨）
- Review Items（人間判断）
- Implementation Readiness（実装に渡せる状態か）
- Fix Recommendation（修正方針）
- Remaining Risks（残るリスク）

### Remaining Risks の扱い

残ったリスク・未対応は、**「今回修正する」か「Deferred として引き渡し Backlog へ送る」かを 1 件ずつ切り分ける**。

- 今回修正するもの → **Fix Recommendation** に回す。
- Deferred にするもの → **理由・再確認条件・判断先**を明記し、引き渡し Backlog（`handoff.md`）へ引き継ぐ。詳細な書式は `handoff.md`「未確定事項 / Backlog の書き方」を参照（ここでは**切り分けと引き継ぎ導線**に絞る）。

### 指摘 1 件あたりの書き方

メインのエージェントが修正に使えるよう、自然文だけにしない。

```text
Issue ID: UI-001
Severity: High
Target: S-001 / 検索エリア
Problem: 主要操作が不明確
Reason: 検索・新規登録・出力の視覚優先度が同等
Fix: 新規登録を Primary、検索を Secondary、出力を Tertiary に分ける
Related: structure.md / 該当画面定義
Expected: 主要操作の優先順位が明確になる
```
