# Design Readiness Check（着手チェック）

要件定義 md を受け取ったとき、デザイン工程に進める状態かを確認するためのルール。デザインフェーズの最初（①）で使う。

目的は、**AI が仕様を勝手に補完して暴走する前に、足りない情報を洗い出して人間に確認する**こと。

## チェック観点

要件 md に次の情報があるかを確認する。

- 画面一覧
- ロール / 権限差分
- 業務フロー
- ユーザーフロー
- 各画面の表示項目
- 入力項目（必須／任意）
- 状態・エラー
- 画面遷移
- 非機能要件・制約
- デザインに必要な業務背景（誰が・何のために・どの順で使うか）
- 各表示項目が「どの実データ項目」を指すか（名称／ID／コード／シリアル／機器名／位置情報 等）と、**取得元**（自動取得／手入力／設定値／外部連携）・**null 時表示**が仕様から読み取れるか
- 保存・取得される項目について、**どの画面に表示するか／表示しない前提かが定義されているか**（保存はするが表示先が未定、がないか）
- 1 画面が複数の進行状態を持つ処理（測定中・通信中など）で、**各状態と遷移条件**が仕様から洗い出せるか

> 開発用の要件 md には、デザイン判断に必要な情報（業務背景・ユーザーフローなど）が抜けていることが多い。そこを早期に見つけるのがこの工程の役目。

## UX 観点チェック

仕様（要件 md）には明記されにくいが、デザイン品質に直結する観点。抜けていれば「仮置き提案＋確認事項」として出す。

- 空状態（データ 0 件）の見せ方が定義されているか
- ローディング / 処理中の表示が定義されているか
- 成功フィードバック（保存・登録・送信完了の通知・トースト）があるか
- エラー時の復帰導線（戻る・再試行）が定義されているか
- 破壊的操作（削除など）の確認ダイアログがあるか
- 主要操作（CTA）の位置・優先度が明確か
- 長いフォーム / リストのスクロール・固定要素（下部固定ボタン等）の方針
- 入力中のバリデーション・エラー表示位置

### 業務システムで特に確認する（操作レベル UX）

以下は「仕様に定義があるか」を確認する観点。定義が無ければ勝手に決めず **PM/仕様確認**へ回す（no-add 原則）。

- **重要操作の事前明示**：影響の大きい操作（課金・送信・申請・削除・重要な設定変更）で、実行前に示すべき情報（条件・影響範囲・通知先・反映タイミング・変更/取消可否）が定義されているか（通知先・反映タイミング・可否は PM/仕様確認）
- **変更前後の差分確認**：設定変更・マスタ編集・金額/申請内容の変更などで、確定前に「変更前→変更後」と影響範囲を示す必要があるか、差分として何を見せるべきかが定義されているか（差分対象・影響範囲は PM/仕様確認）
- **権限・操作可否・不可理由**：権限・ロール別に「見える情報／できる操作／できない操作」と、不可時の扱い（非表示／disabled＋理由／説明付きエラー）が定義されているか（可否の内容は PM/仕様確認）
- **中断復帰**：長い入力・重要入力で、一時保存の要否／未保存のまま離脱・戻る・セッション切れ時の扱い／再開時の復帰が定義されているか（保存挙動は PM/仕様確認）
- **取り消し・キャンセル・復元**：キャンセル／戻る／取り消し（undo）／復元の扱いが定義されているか。未保存入力の破棄確認、削除後の復元可否、取消可能時間は PM/仕様確認
- **ステータス可視化・次アクション**：業務プロセスの現在地（ステータス）・遷移条件・次に誰が何をするか・差戻し時の導線が定義されているか（業務フローは PM/仕様確認）
- **入力負担の軽減**：再入力の回避（既定値・自動補完・自動取得）が可能か、その取得元が定義されているか（取得可否・元データは PM/仕様確認）
- **業務例外・競合・失敗**：業務ルール由来の例外（締切後不可／承認後変更不可／他ユーザー更新済み／対象削除済み／外部連携失敗／在庫・枠不足 等）と、その復帰導線が定義されているか（例外条件は PM/仕様確認）
- **困ったときの導線**：入力例・用語説明・問い合わせ先・エラーコード等の解決導線が必要か／定義されているか（要否・問い合わせ先は PM/運用確認。社外向け・低頻度・専門用語が多い案件では優先度を上げる）
- **一括操作・複数選択**：一括操作の可否・対象範囲（現ページ/全件）が定義されているか（可否・範囲は PM/仕様確認）
- **迷い・離脱・不安ポイント**：主要画面ごとに「どこで迷うか／間違えそうか／不安になるか／離脱しそうか」を洗い出し、対策（導線・文言・確認・安心材料）を検討したか
- **ユーザーの言葉・自然な業務順序**：UI 文言・項目名・画面順が、DB 名/開発者用語ではなく利用者の業務語彙・業務順序に沿っているか（不明な用語・業務順序は PM/業務担当確認）

> ここで挙がった「仕様に無いが必要な UX 要素」は、ワイヤーフレーム段階で状態・エラーとして可視化し、必要なら要件側へ確認する。

`docs/internal/design/01-readiness-check.md` に次を出力する。

- 揃っている情報
- 不足している情報
- 未確定の仕様
- PM に確認が必要な事項
- クライアントに確認が必要な事項
- デザイン側で仮置き可能な事項
- 次工程に進むための条件

## 質問の分類と終了条件

確認事項は **重要度** と **振り分け先** で扱う。

| 分類             | 意味                      | 対応                               |
| ---------------- | ------------------------- | ---------------------------------- |
| **Critical**     | 決まらないと着手できない  | 判定 **Stop**。0 件を目指す        |
| **Warning**      | 後で手戻りになりやすい    | 影響・対応方針を明記すれば進行可   |
| **Review**       | Human/PM/顧客の判断が必要 | 既存「PM／クライアント確認」へ     |
| **Assumption**   | 仮置きして進める前提      | 既存「仮置き可能」へ（前提を明記） |
| **Deferred**     | 今回は見送り              | 見送り理由・再確認条件を明記       |
| **Out of Scope** | デザイン対象外            | 対象外として記録                   |

**終了条件**：**この着手チェックで定義した確認範囲内で**、Critical が 0 件になるまで確認を続ける。0 件になったら**観点を変えて最大 2 回**走査して終了する（**1 回目＝画面・状態・遷移起点／2 回目＝表示データ・取得元・データ要件起点**）。Warning / Review / Assumption / Deferred は残ってよい（判断先・仮前提・見送り理由を明記する）。

## 判定

| 判定           | 内容                             |
| -------------- | -------------------------------- |
| Go             | そのまま次工程（画面整理）へ進む |
| Conditional Go | 仮置き条件を明記して進む         |
| Stop           | 追加確認後に再開する             |

推測で進めない。不明点は「確認事項」として出す（★CP1 で人間／PM が確認する）。
