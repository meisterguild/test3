# External Review Guide（外部レビュー依頼）

自己レビュー（self-review.md）に加えて、制作に関与していない外部レビュアーに第三者レビューを依頼するための観点と依頼文テンプレート。レビュアーは別の AI エージェントか人間のどちらでもよく、特定の製品・エージェントには依存しない。どのレビュアーを使うかは案件側で決める。

## 文面の中立性（報告・確認・レビュー依頼の汎用ルール）

作業エージェントが出す**報告・確認・レビュー依頼の文面**では、特定の役割名・人格名・組織名（例：「〇〇統括レビュー」「統括確認」など）を書かず、**中立表現**を用いる。

- 使う語の例：「レビュー結果」「確認結果」「最終確認」「判断」「レビュー担当」など。
- レビュアー（外部 AI／人間／その他）が変わっても再利用できるよう、依頼文・報告文は**レビュアーの呼称に依存しない**汎用文面にする。
- ツールの事実記載（どの外部 AI に渡すか等）と、報告文への人格・役割ラベルの埋め込みは別。後者を避ける。

## 受け渡し方法

作業エージェントから外部レビュアーを直接呼べない場合は、**人間が橋渡しする**。

1. 作業エージェントが Figma を生成し、レビュー依頼文（このファイルの観点 + Figma の共有 URL）を用意する
2. 人間がそれを外部レビュアーに渡す
3. 外部レビュアーが Figma を見てレビューを返す
4. 人間が結果を作業エージェントに渡し、修正する

> レビュアーが Figma URL から直接デザインを参照できない場合は、スクリーンショットを併用する。

## デザインレビュー（UX・見た目）

見てほしい観点：

- 情報の優先順位は適切か（主要操作が目立つか）
- 余白・情報密度・視覚階層・整列・強調の段階に違和感はないか
- 画面間で一貫しているか
- ユーザーの目的が達成できる導線か
- 操作レベル UX：状態・起点（操作の入口）・復帰導線・重要操作の事前明示・操作不可の理由が押さえられているか
- ユーザビリティ観点：状態の可視性・記憶より認識・実世界/業務語彙との一致・エラー防止と回復
- ユーザーの業務語彙・自然な業務順序になっているか
- 業務上の使いやすさ
- 指摘は **A（機械的に直せる）／B（設計として再検討）／C（Human 判断に回す）** で分けて返してもらえると扱いやすい

### 依頼文テンプレート（デザインレビュー）

```text
あなたは UX/UI デザインレビュアーです。
以下の Figma デザインを、UX と見た目の観点でレビューしてください。
特に「情報の優先順位・主操作」「余白・密度・視覚階層・整列」「操作レベル UX（状態・起点・復帰・事前明示・操作不可の理由）」「業務語彙・自然な順序」「画面間の一貫性」を見てください。
指摘は、対象画面 / 問題 / 理由 / 改善案 の形で、かつ A（機械的に直せる）／B（設計として再検討）／C（Human 判断）に分けてお願いします。
Figma URL: <ここに URL>
```

## 構造レビュー（実装・Figma 構造）

見てほしい観点：

- Figma 構造が実装しやすいか
- Component 分解の粒度は適切か
- 状態・エラーが実装視点で揃っているか
- 命名・レイヤー構造が実装に耐えるか
- Issue 化・テスト設計につなげられるか

### 依頼文テンプレート（構造レビュー）

```text
あなたは実装観点のレビュアーです。
以下の Figma デザインを、フロントエンド実装の観点でレビューしてください。
特に「Component 分解の粒度」「Figma 構造の実装しやすさ」「状態・エラーの網羅」を見てください。
指摘は、対象 / 問題 / 理由 / 改善案 の形でお願いします。
Figma URL: <ここに URL>
```

## 結果の扱い

レビュー結果は `docs/internal/design/05-review` に保存する。自己レビュー（self-review.md の形式）と同じく、Issue 単位で修正に使える形に整理する。
