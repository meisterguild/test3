# Quality（品質・アンチパターン・アクセシビリティ）

見た目の品質を保ち、AI 特有の「それっぽいけど中身の薄い UI」化を防ぐためのルール。デザイン生成時と自己レビュー時に参照する。

## Visual Quality（視覚品質の“正の手順”）

「避けること」だけでなく「こう作る」を示す。ただし視覚品質は過剰にルール化すると量産的で冷たい UI になる。役割で切り分ける：**A＝壊れていないか（機械チェック）／B＝設計として筋が通るか（独立レビュー）／C＝Human 品質として成立するか（人間の最終判断）**。

### 余白（Spacing）

- **原則(B)**：近接＝関係の強さを余白で表す（近いほど狭く、遠いほど広く）。
- **意味↔トークンの目安**（値は tokens-and-scales.md の Spacing スケール）：
  - 要素内 Padding：4 / 8 / 12
  - 項目間 Gap：8 / 12 / 16
  - 関連グループ間：16 / 24 / 32
  - セクション間：32 / 40 / 48
  - ページ大区切り・Section 外余白：48 / 64 / 80
  - 業務システムは基本詰め気味でよい。ダッシュボード/確認画面など大区切りでは 48/64/80 も使う。
- **A（壊れていないか）**：Spacing スケールを使っているか（直値でない）。`要素内 < 項目間 < グループ間 < セクション間` を基本目安とし、大きく逆転している場合は警告する（ただしコンポーネント内 Padding・カード内余白など役割上の例外は B/C で判断）。
- **C に残す**：余白の気持ちよさ・業務密度としてのちょうどよさ・呼吸感（Human 校正）。

### 密度（Density）

- **原則**：均等に置かない。重要な情報群は余白を広めに呼吸させ、補助・一覧は密に。まとまりは余白で作り、線・枠・カードで囲みすぎない。
- **A（異常検知のみ）**：すべて均等／カード過剰／枠線過剰／情報量が極端に薄い／テキストや操作要素が重なる／読めない／タップ領域を侵害している。
- **C に残す**：詰め具合がちょうどよいか（業務系としてどの程度詰めるか）は Human 校正。

### 視覚階層（Hierarchy）

- **手順(B)**：① 優先度を決める（主役1／準主役2–3／その他）→ ② 複数の視覚手段で差をつける（サイズ・ウェイト・色・余白・位置。1手段に頼らない）→ ③ 視線の流れを作る（開始点＝最重要、終了点＝主操作/次アクション。上→下・左→右）。
- **A（壊れていないか）**：タイポ階層が 3–4 段以内か／主操作（Primary）が乱立していないか／強調色が乱用されていないか。
- **B/C に残す**：何を主役にするか・どの視覚手段で立てるか・視線誘導が自然か(B)、最終的な主役判断・重心(C)。

### 整列・グリッド

- 共通の基準線・グリッドに揃える（左揃え基準、端の不揃いを作らない）。列/カラムは Layout Grid で管理（tokens-and-scales の Breakpoint/Grid）。
- **A**：同一列の端の不揃い／同一役割要素の幅・高さの不揃い／小数点座標／はみ出し、を検知。
- **B**：ベースライン・ラベル位置・列幅・グリッドの取り方の妥当性。

### グルーピング手段の選択（余白 / 罫線 / カード）

- まず**余白**でまとめる。余白で足りないときだけ**罫線**、独立した情報塊のときだけ**カード**。囲みは最小限（罫線・カードの多用は密度を下げ量産的になる）。
- **B/C**：どの手段が最適かは情報構造・業務文脈で判断。

### コントラストと強調の段階

- 強調は段階を決める（主役＝最も強い1つ／準主役＝中／その他＝地）。強調手段（サイズ・ウェイト・色）を盛りすぎない。色による強調は最小適用（ui-ux-principles.md「状態色は最小適用」と整合）。
- **A**：強調色・太字の乱用検知。**B/C**：強弱の効き方・上品さ。

### 画面種別ごとの密度方針（目安・C 校正前提）

- **一覧**：情報量多め・行は密に、余白は列間で最小限。
- **フォーム**：ラベルと入力の関係を余白で明確に、グループ間はしっかり空ける。
- **詳細**：読ませる。項目間に呼吸、重要属性を階層で立てる。
- **ダッシュボード**：区画を大区切りの余白（48/64/80）で分ける。
- **確認画面**：確認対象・変更点・影響範囲を明確にし、実行ボタンは主操作として認識できる範囲で過剰に強調しない。破壊的操作ではキャンセルとの関係・危険性の伝達を優先する。
- ※各値・詰め具合は業務文脈で Human 校正。

### 視覚品質レビューの出力観点

レビュー時は、A/B/C を混ぜずに分けて報告する。

- **A**：スケール外の値・余白の大きな逆転・はみ出し・強調色の乱用・タイポ階層過多など、機械的に検出できる問題。
- **B**：余白・密度・階層・整列・グルーピングが、画面目的と情報構造に対して妥当か。
- **C**：Human 品質としての余白感・重心・信頼感・ブランドらしさ・業務密度のちょうどよさ。

作業エージェントは B/C を確定しない。B/C は「レビュー観点・懸念・候補」として出し、最終判断は外部レビュアー / Human に渡す。

### 避けること（AI っぽい量産 UI の典型）

- 過剰な中央揃え
- 均等すぎる余白
- 過剰な Shadow / 過剰な角丸
- 意味のない Hero / 全画面 Card UI / 無意味な Grid
- 情報量が薄いスカスカ UI
- 装飾目的だけのレイヤー

## ワイヤーフレームの配色（グレースケール＋危険1色）

ワイヤーフレームはグレースケール基調にする（情報構造・導線に集中させ、見た目の議論に逸れないため）。

ただし**例外が1つある**：ユーザーが即座に識別すべき**最重要シグナル（危険・エラー・警告の状態）**は、グレー / 黒のままだと「ボタンなのか・メッセージなのか・エラーなのか」がパッと見で判別できない。そのため、これらは **1 色のセマンティックアクセント（危険 = 赤）で区別する**。

- 適用対象：危険・エラー・警告の1系統に**限定**する（例：エラー・危険な状態の強調、削除など破壊的操作のボタン）
- 乱用しない。WF で色がつくのは「危険1色」だけ。それ以外はグレースケールを保つ
- 色の値・命名は tokens-and-scales.md の `Error` ロールに従う
- フルの配色・トークン適用はデザイン工程（④）で行う（WF の赤はその予告）

## AI Anti Pattern（生成してはいけないもの）

AI エージェントが暴走しがちなポイント。次は生成しない。

- 過剰 Wrapper / 全画面 Card 化 / 中央揃え乱用 / 過剰 Hero
- 情報量不足 UI / 装飾だけのレイヤー
- 推測で足した Component / State / Variant / Style / Token
- 不要な Auto Layout / HTML タグ Frame

## Accessibility（アクセシビリティ）

見た目だけでなく、実装時に必要な前提を Figma の段階で組み込む。

- 操作できる要素は Focus 状態を持つ
- テキストと背景のコントラストを確保する
- タップ／クリック領域を十分な大きさにする（小さすぎる Tap Area を避ける）
- アイコンだけの操作には、意味が伝わる Label を用意する
- フォーム要素は状態を持つ（Default / Focus / Error / Success / Disabled / ReadOnly）
- 色だけで状態を判断させない

### 必須の状態

Default / Hover / Focus / Pressed / Disabled / Error / Success

### 禁止

- Focus なしのボタン
- コントラスト不足
- Hover だけの状態定義
- Error 状態の未定義
- Label なしのアイコン操作

## Interaction（操作の挙動）

静的なデザインでは失われる挙動を、注釈（Annotation）で補う。

- Hover / Active / Focus / Loading を定義する
- Animation の有無を明記する（動きの詳細な定義は今回スコープ外）
- 例：「Hover 時に背景色変更」「SP 時は Drawer 表示」

> Annotation の付け方・記法は handoff.md を参照。
