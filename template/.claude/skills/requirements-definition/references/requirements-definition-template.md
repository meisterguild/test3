# 要件定義書フォーマット

## 出力ルール

要件定義書は、本ファイルの章立てに従って作成する。  
章番号、見出し名、表形式は原則として維持する。  
要件定義書は、ドラフト版と最終版を分けて作成する。

| 種別    | 出力先                                   | 用途                    |
| ----- | ------------------------------------- | --------------------- |
| ドラフト版 | `docs/internal/requirements-definition-draft/requirements-definition-draft.md` | 社内レビュー、事前確認、顧客確認前の整理用 |
| 最終版   | `docs/deliverables/requirements-definition/requirements-definition.md`       | 顧客合意後、または社内承認後の正式版    |

また、機能仕様は、機能カテゴリごとに`docs/deliverables/features/` 配下にファイルを作成し、`templates/feature-template.md` の形式で記述する。機能仕様はドラフト版と最終版で分けない。  
ファイル数が多くなる場合は、`docs/deliverables/features/` 配下にフォルダを作成しても良い。例：共通機能、管理者、利用者でフォルダを分ける。


情報が不足している場合は、推測で補完せず、以下のいずれかを記載する。

* 【T.B.D】： 実装はするが、現時点で仕様が確定していないもの。
  * 未決事項または顧客確認事項のIDを必ず並記すること。
    * 例：【T.B.D(CQ-001)】、【T.B.D(TBD-001)】
  * 未決事項または顧客確認事項にない場合は、記載しIDを払い出すこと。
* 該当なし：そもそもその機能やシステムにおいて対象外であるもの
* 今後検討：本フェーズ（スコープ）では対応せず、次フェーズ以降に回すもの

未確認事項を確定済みの要件として本文に混ぜてはいけない。

## 共通記載ルール

### 予算に関わる内容は記載しない

要件定義書には、予算、費用、見積金額、契約金額、単価、工数見積、支払い条件など、金銭・予算に関わる内容を記載しない。

以下のような内容は要件定義書に含めない。

* 予算
* 費用
* 見積金額
* 契約金額
* 単価
* 工数見積
* 支払い条件
* 費用対効果
* コスト削減額
* 追加費用
* 予算超過リスク

ただし、費用に直接触れない範囲で、対象範囲や制約に影響する内容は記載してよい。

悪い例:

```text
予算内に収めるため、外部連携機能は対象外とする。
```

良い例:

```text
外部連携機能は本フェーズの対象外とする。
```

### 個人氏名は記載しない

要件定義書には、個人の氏名を記載しない。  
ただし、部署名、グループ名、支店名などは記載してよい。  

### ID付与ルール

IDは、後続工程で参照・追跡が必要なものにのみ付与する。

以下には原則としてIDを付与する。

| 対象     | 接頭辞   | 例         |
| ------ | ----- | --------- |
| 業務要件   | `BR`  | `BR-001`  |
| 機能要件   | `FR`  | `FR-001`  |
| 画面要件   | `UI`  | `UI-001`  |
| データ要件   | `DT`  | `DT-001`  |
| 外部連携要件   | `INT`  | `INT-001`  |
| 非機能要件  | `NFR` | `NFR-001` |
| 未決事項   | `TBD` | `TBD-001` |
| 顧客確認事項 | `CQ`  | `CQ-001`  |
| 受入条件   | `AC`  | `AC-001`  |

補足: 事前確認事項（`docs/internal/requirements-definition-draft/pre_check.md`）のIDは `PC` で固定する。例: `PC-001`

連番は接頭辞のあとにハイフン＋3桁ゼロ埋めとする。例: `FR-001`  
同一分類で1000件を超える場合のみ4桁にする。例: `FR-1000`  


その他の項目には原則としてIDを付与しない。
ただし、プロジェクトの規模が大きく、後続工程で個別参照が必要な場合のみIDを付与してよい。

#### IDを細かくしすぎない

IDは細かすぎる粒度で付けない。

悪い例:

```text
FR-001 顧客名を入力できる
FR-002 電話番号を入力できる
FR-003 メールアドレスを入力できる
FR-004 住所を入力できる
```

良い例:

```text
FR-001 顧客情報を登録できる
```

入力項目、表示項目、バリデーション、エラー処理などの詳細は、機能詳細や画面要件の中で記載する。

### 表の統合ルール

表を分ける目的が弱い場合は、1つの表にまとめる。

以下は必要に応じて統合してよい。

| 統合前               | 統合後         |
| ----------------- | ----------- |
| ペルソナ一覧 / ユーザー種別一覧 | 利用者像・ユーザー種別 |
| 機能構成 / 機能一覧       | 機能一覧        |
| ロール一覧 / 権限一覧      | 権限・ロール要件    |
| 画面要件 / 表示項目       | 画面要件        |
| データ要件 / 項目一覧      | データ要件       |

## ドラフト版のルール

ドラフト版は、社内レビュー、事前確認、顧客確認前の整理を目的とする。

ドラフト版の出力先は以下とする。

```text
docs/internal/requirements-definition-draft/requirements-definition-draft.md
```

ドラフト版には、以下を含めてよい。

* 根拠資料
* 事前確認結果
* 未決事項
* 顧客確認事項
* 仮置きした要件
* 確認中の内容
* 読み込みファイル一覧

ただし、未確認事項を確定済み要件として本文に混ぜてはいけない。  

---

## 最終版のルール

最終版は、顧客合意後、または社内承認後の正式な要件定義書として作成する。

最終版の出力先は以下とする。

```text
docs/deliverables/requirements-definition/requirements-definition.md
```

最終版では、以下のルールを適用する。

### 改訂履歴

最終版の改訂履歴は、版数 `1.0` から開始する。

ドラフト版の改訂履歴は最終版に引き継がない。

例:

| 版数  | 日付 | 変更内容 | 作成者 |
| --- | -- | ---- | --- |
| 1.0 | 未定 | 初版作成 | 未定  |

### 根拠資料の削除

最終版では、以下のような内部確認用情報を削除する。これにより不要になる章・節は削除する。

* 根拠資料
* 事前確認結果
* 読み込みファイル一覧

ドラフト版では根拠資料を記載してよいが、最終版では顧客提出・正式合意に不要な内部情報として扱う。

### 解決済み項目の削除

最終版では、解決済みの「未決事項」「顧客確認事項」は削除する。

未解決のものだけを残す。

すべて解決済みの場合は、章・節を削除する。
