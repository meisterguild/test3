# Code Security Review

指定されたコード（ファイル、ディレクトリ、またはコードスニペット）をセキュリティ観点でレビューし、所見を報告する。**修正は行わない**（指摘・推奨対策の提示まで。コード修正はユーザーが明示依頼した別作業として扱う）。

## 手順

### 1. コードをセキュリティ観点でレビューする

以下のカテゴリを網羅的に確認する。

1. **インジェクション** — SQL/OS/LDAP インジェクション、コマンドインジェクション
2. **XSS / 出力エスケープ** — ユーザー入力のサニタイズ漏れ
3. **認証・認可** — 不適切なアクセス制御、セッション管理の不備
4. **機密情報の露出** — ハードコードされた認証情報、ログへの秘密情報出力
5. **暗号化** — 弱いアルゴリズム、不適切な鍵管理、平文保存
6. **依存関係** — 既知の脆弱性を持つライブラリ（判明している場合）
7. **CSRF / リクエスト偽造**
8. **その他** — エラーハンドリングによる情報漏洩、過剰な権限など

### 2. レポートを出力する

push ゲート (`review-runner.py`) 経由で呼ばれる場合、AI CLI の structured output で JSON を返すため本フォーマットは適用されない（review-runner.py 側で `.claude/last-review.md` に整形される）。

**単独呼び出し時のみ以下のフォーマット** で出力する。整形は push ゲートの出力に合わせる:

```
# セキュリティレビュー結果

## サマリー
- 対象: <ファイル・範囲>
- high: N 件 / medium: N 件 / low: N 件

## 所見

### [<SEVERITY>] <ファイル名>:<行番号>

**指摘:** 問題の内容

**影響:** 悪用された場合のリスク

**修正方針:** 推奨対策（実施はしない）

**カテゴリ:** <インジェクション / XSS / 認証・認可 / 機密情報 / 暗号化 / 依存関係 / CSRF / その他>
```

`<SEVERITY>` は **HIGH / MEDIUM / LOW** の 3 段階。基準:

- **HIGH**: 直接的な攻撃に悪用される可能性が高い
- **MEDIUM**: 条件次第で悪用されうる
- **LOW**: ベストプラクティス違反、悪用には追加条件が必要

所見がない場合は「問題は検出されませんでした」と明記する。

## やらないこと（レビュー実行側）

- **コードの修正実施**: 本 skill のレビュー実行側は指摘までを担当する。ユーザーが明示的に「修正もして」と依頼した場合のみ、別作業として修正を行う（その際もテストが存在するなら修正後に必ず実行する）

# レビュー結果への対応（受け手側、auto / interactive 共通）

ここから先は **本 skill のレビュー結果を受け取った別 claude セッション** が辿るロジック。push ゲート (`review-runner.py`) 経由で本 skill が実行された場合、結果（`findings[]` 形式の JSON）は git push の stdout/stderr 経由で受け取り側の claude に届く。受け取った claude は以下に従って対応する。

## 1. 指摘の分類

各 finding を以下 6 ケースのどれかに分類する。判断根拠を明示する（後工程のレビュアーが検証できるように）:

| # | ケース | 例 | 対応 |
| --- | --- | --- | --- |
| (1) **作業 AI のミス** | バグ / 規約違反を見落とし、よく見れば確かに HIGH の指摘 | コード修正（retry に乗せる） |
| (2) **暫定実装の補填** | 上流工程の漏れで一旦埋めた、設計上は別所で扱うべき | bypass + 「暫定、後で X 修正」を判断ログに記載 |
| (3) **意図的な設計判断** | トレードオフを認識した上での選択（パフォーマンス vs 防御深度等） | bypass + rationale を判断ログに記載 |
| (4) **レビュー AI の false positive** | 指摘内容が誤り、コードは正しい | bypass + false positive 判定の根拠を判断ログに記載 |
| (5) **既存コードで対策済み** | 単体で HIGH に見えるが別所でカバー（middleware / upstream 等） | bypass + 対策箇所への参照を判断ログに記載 |
| (6) **設計レベルの問題** | 仕様が足りない / ADR が要る / 範囲外の判断が必要 | push 中断、`status:blocked` 相当の状態で人間 escalate |

## 2. severity による境界

- **HIGH**: 必ず分類し、(1) なら修正、(2)〜(5) なら明示的な bypass、(6) なら escalate
- **MEDIUM**: HIGH と同じく分類するが、(1) の自動修正は判断次第（軽微なら修正、複雑なら bypass + 記載で進む）
- **LOW**: **修正しない**。分類（多くは (3) 意図的な設計判断 / (4) false positive）と「未対応」の判断を判断ログに**必ず記載**して先へ進む

**low 単独で追加ラウンドを起こしてはならない。** HIGH / MEDIUM を修正するラウンドで、同じ箇所を触るついでに low を直すのは構わない（そのラウンドの中で完結する限り）。禁止するのは「low を直すこと自体を目的にした再 push」である。

> **なぜ LOW を「修正可能なら修正」から変えたか:** ゲートの既定（`review-config.yml` の `depth: low`）は「low / medium / high の全てを、改善余地も含めて網羅的に」報告させるため、**毎ラウンド必ず何かが出る**。そこで「low を直す → 再 push → hook 再評価」を既定にすると終端が存在しなくなる。実測で 6 ラウンド・約 70 分を消費し、high は全ラウンド 0 件（= push は一度もブロックされていない）という事例がある。網羅的な検出は本物の medium を拾うために維持する価値があるので、**検出は変えず、止め方をこのルールで縛る**。

## 3. 判断ログの記録先

claude が分類と対応を行ったら、**必ず判断ログを残す**:

- 記録先: PR description の「AI レビュー結果」セクション（PR 作成後）、または `.local/pr-draft-<branch>.md`（PR 作成前）
- 形式は構造化: severity / file / line / **関心事タグ** / 分類 (1〜6) / 判断 / 理由
- **関心事タグ**は `<ファイル>:<関心事>` 形式の短い識別子（例 `ComboBox.tsx:aria-expanded と listbox の整合`）。§5 の打ち切り検知がこれを入力にする
- (1) の修正で通った指摘は記載不要（コード自体が解決を示す）

## 4. 終端条件

### 4.1 ラウンドの数え方と上限

**1 ラウンド = ゲート (`review-runner.py`) が findings を返した 1 回**。hook が push を止めたかどうかは関係ない。

- **上限は 2 ラウンド。3 ラウンド目に入ってはならない。**
- 3 ラウンド目が必要に見えたら、それは修正が次の指摘を生んでいる状態（自己増殖）である。§5 の打ち切り検知に従い、修正を続けず bypass / escalate に切り替える
- push 済みの commit へ追加修正を重ねても、ゲートの差分範囲（`upstream..HEAD`）が空になりゲート自体が再評価されない。レビューされないラウンドを増やしても品質は上がらない

### 4.2 判定

全 finding 処理後、上から順に最初に当てはまる行の対応を取る:

| # | findings の状態 | 対応 |
| --- | --- | --- |
| a | (6) を含む | 修正せず終端。push を諦め、`status:blocked` で人間 escalate（呼び出し側 wrapper skill） |
| b | **high 0 件かつ medium 0 件**（残るのは low だけ） | **修正せず終端**。low の一覧と「未対応」の判断を判断ログに記載する（追加ラウンドを起こさない） |
| c | 1 ラウンド目 かつ (1) 系の high / medium がある | 修正して再 push で hook 再評価（→ 2 ラウンド目） |
| d | 2 ラウンド目 かつ high が残っている | **上限到達**。修正を続けず §5 の判定に従って (4) bypass / (6) escalate。bypass する場合は「2 ラウンド上限で打ち切った」ことと残った high の内容・根拠を判断ログに必ず記載する |
| e | 2 ラウンド目 かつ high 0 件（medium / low が残っている） | 修正せず終端。判断ログに記載する |
| f | 上記以外で (2)〜(5) を含む | 修正せず終端。判断ログに記載する |

### 4.3 終端時の push

(6) で escalate する場合を除き、終端したら push する。hook が止めるなら bypass で押し切る（hook 通過の具体は呼び出し側 wrapper skill の責務、auto mode は `--no-verify` 等）。**bypass するときは判断ログの記載が必須**（§3）。

## 5. 打ち切り検知（同一指摘 / 同一関心事の繰り返し）

次のどちらかに当てはまったら、それは **(1) の純粋ミスではない**:

1. **同一指摘の繰り返し** — 同じ指摘が 2 回以上出続けた
2. **同一関心事の 2 ラウンド連続** — 指摘の文面は違うが、**同一ファイルの同一関心事**に対する指摘が 2 ラウンド連続で出た

どちらかが成立したら判断を見直し:
- (4) false positive 寄り
- (6) 設計レベルの問題

の可能性を疑って、bypass / escalate に切り替える。**修正を続けない。**

### 「同一関心事」の判定

**関心事 = 1 つの機能単位。** ファイルより細かく、行より粗い（例: 1 コンポーネントの ARIA 属性の整合、1 つのバリデーション経路、1 つの CSS レイアウト規則、1 つのエラーハンドリング方針）。

判定できるようにするため、**判断ログの finding ごとに「関心事タグ」を書く**（`<ファイル>:<関心事>` 形式の短い識別子。例 `ComboBox.tsx:aria-expanded と listbox の整合`）。次のラウンドの finding が既に書いたタグと一致したら、**指摘の文面が違っても同一関心事**とみなす。

**最も強いシグナルは「直前のラウンドで自分が修正した箇所を、また指摘されている」こと。** これは修正が次の指摘を生んでいる（自己増殖）状態で、書き直しを重ねても収束しない。この場合は修正せず bypass する。

> **実例:** 同一コンポーネントの 30 行程度の ARIA ロジックについて、`空の listbox を描画している` → `aria-expanded と onClick の基準が不整合` → `popup は見えているのに aria-expanded が false` → `二重ラッパー / 実効の無い CSS が残った` → `hidden 属性がテストで未検証` と、**毎ラウンド違う指摘**が続いて 6 ラウンド回った事例がある。1.（同一指摘）だけでは 1 度も発火しなかった。2. があれば 3 ラウンド目で止まっていた。

## Mode 別の差分

| 項目 | interactive | auto |
| --- | --- | --- |
| 分類判断 | 人間と相談しながら | claude 単独で判断 |
| 修正 retry | 人間が承認してから（上限 2 ラウンドを既定とし、超えるには人間の明示指示が必要） | claude が判断。**最大 2 ラウンド**（§4.1）。high 0 件なら追加ラウンドを起こさない。同一指摘 / 同一関心事の 2 ラウンド連続で打ち切り（§5） |
| bypass の最終決定 | 人間が承認 | claude 単独で判断、判断ログを必ず記載 |
| (6) escalate の窓口 | 人間と対話 | `status:blocked` ラベル付与（呼び出し側 wrapper skill: `git-commit-auto` / `github-pr-auto`） |
