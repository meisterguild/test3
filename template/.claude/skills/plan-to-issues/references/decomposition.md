# タスク分解と issue マッピングの規約

## 基本方針: 根拠ID駆動で「漏れなく・AIが理解しやすい」粒度にする

タスクは要件・設計の **根拠ID から導出する**。これにより (1) 取りこぼしをカバレッジ表で機械的に検出でき、(2) 各 issue が「どの仕様に従うか」を一意に持てる。根拠IDに紐づかない作業は起票しない（創作の禁止）。

**粒度の基準**: 1タスク = 「実装エージェントが1つの作業として着手・完了できる最小の意味単位」。

- 大きすぎ（例: 「システム全体を実装」）→ 分割する。
- 小さすぎ（例: 「関数を1つ書く」）→ まとめる。詳細設計・実装手順の粒度には落とさない。
- 目安: 1タスクの DoD が 2〜6 個のチェック項目で書ける程度。

## 入力ステージ別の切り出し方

フェーズ1で判定した入力ステージにより、既定の切り出しを変える。

| ステージ | 状態 | 既定の切り出し | 主な type/テンプレ |
| --- | --- | --- | --- |
| A | 要件定義書のみ（設計未着手） | 機能グループ単位で **仕様策定** タスク。実装 issue は時期尚早なので既定では起こさない（ユーザーが求めれば feat も） | `spec.md` → `type:docs` |
| B | 基本設計書あり（設計済み） | 設計＝真理ソースが既に存在 → **spec issue は重複させない**。機能／設計判断単位で実装タスク（必要なら test-design とのペア） | `feat.md` → `type:feat`、`test-design.md` → `type:test` |

判定に迷う入力（要件定義書＋一部設計など）は、フェーズ1でユーザーに確認する。headless では設計書の有無で機械的に A/B を決める。

## 粒度プロファイル（`--granularity` で上書き）

- **`feature`（既定）**: 機能／設計単位に 1 タスクへ集約する。type は内容で判定。小〜中規模・実装重視向け。
- **`layered`**: 1 機能を `spec.md`（仕様＝設計docs）→ `test-design.md`（テスト設計）→ `feat.md`（実装）に分割する。品質ゲートを重視する場合や spec が未整備の場合向け。issue 数は増える。
  - **束ね方（新原則・下記「依存・親子の記録」と統一）**: 機能グループごとに **取りまとめ親 1 件＋子3件**（子＝設計docs / テスト設計test / 実装feat）を起こす。親は分割前の機能グループを取りまとめる箱（別立ての新規起票）で、既存の作業タスクを親に流用しない。子3件の間だけを **設計→テスト設計→実装** の blocked-by で繋ぐ。**親はどの子とも blocked-by で繋がない**（親を依存チェーンに入れない）。
  - ステージB（設計済み＝spec 相当が存在）では 設計docs の子を作らず、**取りまとめ親＋子2件（`test-design`・`feat`）** を既定とする。blocked-by は `test-design`→`feat` のみ。

## type / テンプレ判定

判定の**唯一の根拠**は `.claude/skills/github-issue/references/github-issue.md` の「テンプレート」表と type 体系。ここでは入力ドキュメントの性質から出発点を示すのみ（最終判定は github-issue 規約に従う）。

| 入力の出どころ・内容 | テンプレ | label |
| --- | --- | --- |
| 機能要件 FR／設計の機能・API・画面の新規実装 | `feat.md` | `type:feat` |
| 仕様そのものの策定・変更（spec 未確定） | `spec.md` | `type:docs` |
| テスト設計（AC/R 抽出・it.todo 雛形） | `test-design.md` | `type:test` |
| 非機能要件 NFR 由来の性能改善 | `perf.md` | `type:perf` |
| 既存構造の入れ替え・技術的負債の解消 | `refactor.md` | `type:refactor` |
| specs 以外のドキュメント整備 | `docs-other.md` | `type:docs` |
| ビルド・依存・環境・運用整備 | `chore.md` | `type:chore` |
| 判別不能 | フェーズ1で確認 / headless は `chore.md` | — |

### 取りまとめ親（sub-issue の親）の type

layered などで子課題を束ねる取りまとめ親の type は、固定（`chore` 等）にせず **子に合わせる**。

- 子が単一 type ならその type に合わせる。
- layered のように子が docs/test/feat と複数 type にまたがる場合は、そのグループの成果の中心＝**実装(feat)** に合わせる（機能グループ全体を feat の取りまとめとして扱う）。
- 勝手に新 type を作らない。テンプレは上表と `github-issue` 規約に従う。

## トレーサビリティ（要件ID ↔ issue）

`github-issue` のテンプレート本文の節を **改変せずに** 使い、次の対応で情報を流し込む。

### `feat.md` の場合

- **「対象 spec（真理ソース）」**: 入力設計書のパス＋該当セクション（例 `docs/deliverables/functional-design/03-api.md#ユーザー登録api`）。ステージA でこれから spec を作る場合は「(本 issue で新規作成)」。
- **「経緯・関連」**: 根拠IDを `根拠: FR-03, R-01, D-02` の形式で。関連 issue は起票後に relationship で表現するため、ここには根拠IDを主に書く。
- **「実装範囲」**: 設計書から読み取れる影響箇所（クライアント/API/DB/インフラ）。
- **「完了条件 (DoD)」**: 受入条件 `AC-xx` や設計の受入基準から具体項目を起こす。
- **「補足」**: `task-id`（逆引き用。例 `task-id: T-03`）。

### `spec.md` の場合

- **「対象機能」**: area/feature 名。
- **「仕様書」**: 対象 spec パス（新規なら「(本 issue で新規作成)」）。
- **「AC / R 候補」**: 要件定義書の AC・NFR から素案を拾う。
- **「関連」**: 根拠ID＋`task-id`。

### `test-design.md` の場合

- 対象 spec（真理ソース）に設計書/要件のパス、AC/R の抽出元IDを明記。

## 優先度の写像

- 要件・設計に優先度情報があれば `priority:high|mid|low` に写像する。
- 無ければ **付けない**（`github-issue` の「priority は任意」規約を尊重）。自分から優先度を創作しない。

## 依存・親子の記録（task-id ベース）

issue 番号は起票まで未確定なので、計画段階では **task-id** で関係を持つ。

- **親子（sub-issue）＝構造**: 分割前の課題を取りまとめる関係。「親 task-id」列に記録。
  - **親は「取りまとめの箱」**。複数の子課題をグルーピングするだけの存在で、それ自体は作業ステップでも依存チェーンの一員でもない。
  - 親は **別立ての取りまとめ課題として新規に起票する**。既存の作業タスク（設計 等）を親に流用しない。
  - 親の 根拠ID は、子の 根拠ID を束ねた **機能グループ単位**（親単体で新規に根拠を創作しない）。type は上記「取りまとめ親の type」に従う。
- **blocked-by（依存）＝順序**: 「A が終わらないと B に着手できない」先行依存。「blocked-by task-id」列に記録。
  - **blocked-by は兄弟（子）同士にのみ張る。親と子の間には blocked-by を絶対に張らない**（親を依存チェーンに入れない）。
- **親子（構造）と blocked-by（順序）は意味が違う。同一ペアに両方を重ねて張ることを禁止する**（親子で繋いだペアを blocked-by でも繋がない）。
- 依存グラフに循環があってはならない（フェーズ3のレビュー観点）。
