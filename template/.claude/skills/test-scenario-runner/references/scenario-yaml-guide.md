# シナリオYAMLの読み方

test-scenario-writer スキルが仕様書から抽出したテストシナリオの中間形式。**特定のテストフレームワーク・ツールに依存しない**自然言語ベースの記述で、仕様書と動作確認結果の間のトレーサビリティを担う。スキーマの正本（書くためのルール・抽出ルール）は test-scenario-writer 側の `references/scenario-schema.md` — 本ガイドは動作確認の実行に必要な読み方だけをまとめる。

## 構造

```yaml
meta:
  source: docs/勤怠管理_要件定義書.txt # 元仕様書のパス（複数可）
  system: 勤怠管理システム # 対象システム名 — レポートの表題に使う
  prefix: ATT # シナリオIDの接頭辞

scenarios:
  - id: ATT-LOGIN-004 # 証跡ファイル名・レポートの行に使う一意ID
    source_ref: 第2章 ログイン画面 > ログインフォーム > ログインボタン # 仕様書内の位置
    screen: ログイン画面
    title: 認証成功時にダッシュボードへ遷移する
    type: transition # display / input-validation / transition / state / error / permission
    priority: high # high | medium | low — 実行順や部分実行時の選定の参考
    preconditions: # 実行前に満たすべきデータ・状態。満たせなければ BLOCKED
      - 有効なユーザーが登録済み
    steps: # ユーザー操作（自然言語・1行1操作）→ 操作スクリプトの操作に対応させる
      - ログイン画面を開く
      - メールアドレスとパスワードを入力する
      - ログインボタンをクリックする
    expected: # 検証項目（自然言語・1行1確認ポイント）→ 確認ポイント＋スクリーンショットに対応させる
      - ダッシュボード画面へ遷移する
    notes: "" # 曖昧な仕様の補完・データ準備の注意 — 実行前に必ず読む

unmapped: # E2Eシナリオにしなかった要件。レポートへの転記対象
  - source_ref: ...
    requirement: ...
    disposition: other-layer # 下表参照
    layer: unit
    reason: ...
```

## 実行時の解釈ルール

- `steps` / `expected` はツール非依存の自然言語 — セレクタ・URL等の具体要素は**実装を調査して実行時に特定する**（SKILL.md の Phase 2）
- `expected` の判定範囲は書かれている文言まで。書かれていない詳細（具体的なメッセージ文言等）は判定基準にせず、観察結果としてレポートに記録する
- `notes` に補完解釈が書かれているシナリオは、その解釈を前提に確認し、レポートの備考にも引き継ぐ

## unmapped の disposition と実行時の扱い

| disposition    | 意味                                              | 実行時にやること                                                                                                                                                       |
| -------------- | ------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `other-layer`  | E2E非適。`layer`（unit / feature 等）で検証する   | レポートの引き継ぎ事項に転記（テスト先レイヤを明記）                                                                                                                   |
| `impl-pending` | 原理的に検証可能だが抽出時点で実装が未確認/未実装 | **Phase 1 で実装に照らして最終判定する** — 手動実行できるコマンドやシードで再現できればシナリオに昇格して動作確認。無理なら据え置き、`revisit`（再追加の契機）を最新化 |
| `untestable`   | 自動テストで検証不能（実決済・外部API等）         | レポートの対象外一覧に転記                                                                                                                                             |
