# /test-scenario-runner コマンド

作成済みのテストシナリオYAMLに沿って、実アプリを自動操作で動作確認して**証跡とレポート**を残すワークフローです。シナリオはツール非依存なので、操作手段はアプリの形態（Web / ネイティブ / モバイル / CLI など）に合わせて選びます。

```text
シナリオYAML（ツール非依存）  docs/deliverables/test-scenarios/<slug>.yaml
   │  Phase 1-2: シナリオと実装のマッピング → 自動操作で動作確認（各検証ポイントで証跡取得）
   ▼
証跡 + 確認結果レポート  <証跡出力先>/<slug>/<実行日時>/
```

入力のシナリオYAMLは **test-scenario-writer スキル**で作成する。YAMLの構造と各フィールドの読み方は [references/scenario-yaml-guide.md](references/scenario-yaml-guide.md) を参照（**動作確認を始める前に必ず読む**）。

## 使い方

| 呼び出し                                   | 動作                                              |
| ------------------------------------------ | ------------------------------------------------- |
| `/test-scenario-runner <yamlパス>`         | 全シナリオを動作確認 → レポート作成               |
| `/test-scenario-runner <yamlパス> <ID...>` | 指定シナリオIDだけ動作確認（例: `ATT-LOGIN-004`） |

シナリオYAMLがまだ無い（仕様書しか無い）場合は、先に `/test-scenario-writer <仕様書パス>` でシナリオを作成し、人のレビューを経てから本スキルを実行する。

## Phase 0: プロジェクト構成の把握

動作確認に入る前に以下を調査して方針を決める:

1. **アプリの起動方法**: プロジェクトのルールドキュメント（`CLAUDE.md`・`.claude/rules/`・`docs/internal/` のテスト方針）から、テスト用環境でのアプリ起動方法・ベースURL・テスト用DBとデータ準備（シーダー等）を確認する
2. **対象アプリが実装済みか**: 動作確認は実装済みアプリが前提。実装が無い場合はここで終了し、実装後に再実行する流れを案内する
3. **操作自動化手段**: アプリの形態に合わせて、動作確認に使えるツールを確認する。プロジェクトに導入済みのものを最優先し、無ければ候補を提案して了承を得てから導入する
   - Webアプリ: ブラウザ自動化ライブラリ（例: Playwright が導入済みならそのライブラリAPIを使う。無ければ `npm install -D playwright && npx playwright install chromium` を提案）
   - ネイティブ・モバイルアプリ: プラットフォームのUI自動化手段（OSの自動化API・シミュレータ/エミュレータ操作・Appium 等）からプロジェクトで利用可能なものを選ぶ
   - CLI・バッチ: コマンド実行と出力の捕捉で足りることが多い（専用ツール不要）
4. **証跡の出力先**: `docs/deliverables/test-evidence/<slug>/<YYYYMMDD-HHMM>/`（実行ごとに作成）。プロジェクトに既存の置き場の慣習があればそちらに従う

## Phase 1: 準備

1. プロジェクトのテスト実行ルール（起動方法・テスト用DB・シーダーによるデータ準備・再実行の制限・DB初期化の扱い等）に従い、テスト用環境でアプリを起動する
2. シナリオの `preconditions` を満たすデータを用意する（既存のシーダー・ヘルパーを優先。満たせない場合そのシナリオは `BLOCKED` とする）
3. **`unmapped` の `impl-pending` 項目を実装に照らして最終判定する**: 該当機能に手動実行できるコマンド（バッチ・artisan コマンド等）やシードで再現できるデータがあれば、シナリオに昇格して動作確認する（シード投入 → コマンド実行 → 画面確認）。無ければ `impl-pending` のまま据え置き `revisit` を最新化する。判定結果はレポートに記録する

## Phase 2: シナリオと実画面のマッピング

シナリオは要件定義の粒度（自然言語）で書かれており、操作・確認する具体的な要素は持っていない。**要素は動作確認の時点で実装から特定する** — 詳細設計書が無くても、この時点ではアプリが実装済みであり、実装そのものを詳細設計の代わりに参照できる。

1. ルーティング/画面遷移定義・ビュー/コンポーネントのコード、または起動済みアプリの実際の画面構造（WebならDOM、ネイティブならUI階層・アクセシビリティツリー等）を調査し、各 `step` の操作対象（画面・入力欄・ボタン）と各 `expected` の確認対象を特定する
2. セレクタ等の実装依存の情報は**使い捨ての操作スクリプトにだけ**書き、シナリオYAMLには書き戻さない（実装が変わってもシナリオは有効なまま）
3. `expected` の判定は**要件に書かれている範囲**で行う。例: 要件が「エラーメッセージを表示する」なら、エラーメッセージが表示されたこと自体を判定し、具体的な文言は判定基準にせず観察結果としてレポートに記録する
4. `step` / `expected` に対応する画面・要素が実装に見つからない場合は、推測で代替せず `NG`（未実装の疑い）または `BLOCKED` とし、「対応する要素が見つからない」という事実をレポートに記録する
5. 要件が曖昧で実装を見て解釈を確定した場合（例: 「一覧を表示」がページングか無限スクロールか）は、採用した解釈をレポートの備考に記録する

## Phase 3: 実行

テストランナー（テストフレームワーク）は使わず、Phase 0 で決めた自動化手段で**一回限りの操作スクリプト**を書いて実行する。シナリオの `steps` を操作に、`expected` を確認ポイントに対応させる。

- **証跡**: シナリオごとに、初期表示・主要操作後・**各検証ポイント（必須）**でスクリーンショットを撮る。ファイル名は `<シナリオID>_<連番2桁>_<内容>.png`（例: `ATT-LOGIN-004_02_dashboard.png`）。画面を持たない対象（CLI・バッチ等）はコマンド出力・ログをファイルに保存して証跡とする
- **判定**: 画面遷移・表示テキスト等の機械チェック可能な項目はスクリプト内で判定して結果をJSON/標準出力に記録する。表示崩れ・画面項目の有無など目視相当の確認は、**取得したスクリーンショットを Read ツールで開いて自分の目で確認**して判定する
- 判定は必ず実際の観察（スクリーンショット・画面構造・出力）に基づく。**実行していない確認を OK と報告しない**
- 固定 `sleep` ではなく明示的な待機（遷移完了・要素表示待ち）を使う

操作スクリプトは証跡ディレクトリに `run-<対象>.<拡張子>`（例: `run-attendance.mjs`）として保存して実行する。Webアプリを Playwright で操作する場合の具体例は [references/run-script-example.md](references/run-script-example.md) を参照（他の手段でも「操作 → 各検証ポイントで証跡取得 → 判定結果を出力」という構成は同じ）。

### 結果の判定

| 結果      | 条件                                   |
| --------- | -------------------------------------- |
| `OK`      | すべての `expected` を確認できた       |
| `NG`      | いずれかの `expected` が満たされない   |
| `BLOCKED` | 前提条件・環境要因で確認に到達できない |
| `SKIP`    | 今回の確認対象外（理由を記録）         |

`NG` の場合は、その時点のスクリーンショット・エラー表示・サーバログから「アプリの不具合」「シナリオ（仕様解釈）の不備」「環境・データ要因」を切り分ける。**アプリの修正は本スキルの範囲外** — 事実と根拠をレポートに記録して報告する（修正はユーザーの指示を待つ）。

## Phase 4: 確認結果レポート

[references/evidence-report.md](references/evidence-report.md) のテンプレートに従い、証跡ディレクトリ直下に `report.md` を作成する。

- サマリー（OK/NG/BLOCKED/SKIP 件数）とシナリオ別結果表（証跡ファイルへの相対リンク付き）
- NG はスクリーンショットを埋め込み、期待値・実際の挙動・原因切り分けを記載する
- `unmapped`（動作確認しなかった要件）も漏れが見えるよう転記する。特に `other-layer`（別レイヤで要テスト）と `impl-pending`（実装後に要追加）は**引き継ぎ事項**として一覧化し、テスト先レイヤ・再追加の契機を明記する

最後にユーザーへ、レポートパス・結果サマリー・NGの要点を報告する。

## 注意事項

- シナリオYAMLは読み取り専用として扱う — 動作確認で得た知見（セレクタ・解釈・NG原因）はレポートに書き、YAMLには書き戻さない。シナリオ自体の不備を見つけた場合は報告し、修正は test-scenario-writer の再実行（仕様書改訂の差分反映）に委ねる
- 認証情報などの秘匿情報はスクリプトに直書きせず環境変数・既存ヘルパーを使う
- 証跡ディレクトリは実行日時で分け、過去の証跡を上書きしない
