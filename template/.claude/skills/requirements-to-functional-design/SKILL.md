# 要件定義書から基本設計書を作る

要件定義書を入力として、基本設計書の一式を生成する。読者は**実装を担当するコーディングエージェント**であり、人間は設計判断の妥当性をレビューする役に回る。したがって背景説明や装飾よりも、曖昧さを排した構造化記述と参照しやすいセクション構造を優先する。

このスキルの最大の失敗モードは、**要件の穴をもっともらしい創作で埋めてしまう**ことだ。要件定義書の品質は保証されていない（不足や矛盾があり得る前提で受け取る）。設計判断に必要な情報が欠けていたら、黙って補完せず必ずユーザーに質問する。後続のフェーズで新たな穴が見つかった場合も、質問に戻ってよい。

## 入出力の規定

- 入力はユーザーが指定した要件・仕様を示す資料一式（複数可）。Markdown を典型とするが、テキスト・PDF・画像など読める形式なら何でも受け取る。未指定なら質問して特定する。
- Figma の URL は Figma MCP で読み取る。MCP が使えない環境では黙って無視せず、エクスポート画像などの代替をユーザーに求める。
- 出力先は `docs/deliverables/functional-design/` を既定とし、ユーザー指定があればそれに従う。
- 出力先にこのスキルの設計書一式が既に存在する場合は、後述の「改定モード」で差分更新する。設計書以外のファイルが存在する場合や、ユーザーが作り直しを明示した場合は、上書きの前に必ずユーザーへ確認する。
- 設計書は入力資料の主たる言語で書く。判断がつかない場合はユーザーに確認する。
- 要件 ID は入力資料の採番を最優先する。資料に要件番号・機能番号（`FN-01`「機能 3.2」など、形式は問わない）が既にあればそのまま使い、独自の番号を振り直さない（振り直すと番号の読み替えが必要になり、トレーサビリティが壊れる）。ID のない項目にだけ、既存の採番体系と紛れない接頭辞の仮 ID（R-01 形式）を採番する。Figma など文書の形をしていない資料から読み取った仕様も、同様に項目化・採番する。要件対応表とレビューのカバー漏れ検証は、この ID を単位として行う。

## 成果物の構成

セクション別の複数ファイルを、番号プレフィックス付きの固定名で生成する。各ファイルのテンプレートと記載項目は `references/templates.md` にある。**執筆を始める前に必ず読むこと。**

```text
docs/deliverables/functional-design/
├── 00-overview.md      # 概要・改訂履歴・設計判断サマリ・要件対応表・読む順序
├── 01-architecture.md  # アーキテクチャ・コンポーネント分割
├── 02-data-model.md    # データ入出力・データモデル・DB設計
├── 03-api.md           # API・外部インターフェース設計
└── 04-ui.md            # 画面設計
```

`00-overview.md` は index を兼ねる。改訂履歴はここに一元管理し、各セクションファイルには持たせない（分散させると更新漏れで履歴自体が信用できなくなるため）。実装エージェントはここから必要なセクションだけを選んで読めるため、ファイル分割の弱点である全体像の喪失を補える。

01〜04 の4セクションは原則すべて必須。省略は次の2経路のみ認める。

- ユーザーからの直接指示（最優先）。
- 案件に該当しないセクション（UI を持たない、DB を持たないなど）について、フェーズ3で省略を提案し、承認を得た場合。

いずれの場合も、省略したセクションと理由を `00-overview.md` に明記する。該当しないセクションを無理に書くと、要件にない創作をスキル自身が生むことになる。

### 規模に応じた分割

1セクション1ファイルは既定であって上限ではない。読者の実装エージェントは必要な箇所だけをコンテキストに読み込むのだから、1ファイルが肥大するとファイル分割の利点そのものが失われる。1ファイルが数百行（目安として500行）を超えそうなとき、またはセクション内に独立した機能群・ドメインが複数あるときは、そのセクションをディレクトリに置き換えて分割する。

```text
docs/deliverables/functional-design/
├── 00-overview.md
├── 01-architecture.md
├── 02-data-model.md
├── 03-api/
│   ├── 00-index.md      # セクション概要・全体一覧表・分割ファイルの担当範囲
│   ├── 01-auth.md
│   └── 02-orders.md
└── 04-ui.md
```

- 分割の単位は機能・ドメインで切る。行数で機械的に切ると、1つの機能を実装するために複数ファイルを読む羽目になる。
- 分割ファイルにも番号プレフィックスを付け、`00-index.md` にセクション全体の一覧表（エンドポイント一覧・画面一覧など）と各ファイルの担当範囲を置く。個別定義は各分割ファイルに置く。テンプレートの見出し構成自体は分割後も維持する。
- `00-overview.md` の「読む順序」と要件対応表の参照先は、ディレクトリ名ではなく分割後の実ファイルを指す。
- 改定モードで反映した結果セクションがこの目安を超えた場合も、このタイミングで分割してよい。その場合は改訂履歴の「更新ファイル」欄に分割したことを記録する。

## 記述の深さ

方針レベルまでを書き、コードは書かない。

- 書かないもの：クラス設計、関数シグネチャ、具体的な実装コード。
- 書くもの：エラー処理方針、認証認可方針、トランザクション境界など、実装者が迷うポイントの方針。

詳細すぎる設計書は実装エージェントの判断余地を奪い、メンテナンスも重くなる。粗すぎると設計書の意味がなくなる。その均衡点をこの境界に置く。

## ワークフロー（初版）

出力先に設計書一式がまだ存在しない場合は、次の6フェーズで進める。フェーズ3の承認より前に設計書の本文を書き始めない。

### 1. 要件定義書の読解と検証

すべての入力資料を読み、「入出力の規定」の要領で要件を項目化・採番する。そのうえで不足・矛盾を洗い出し、設計判断に必要な穴はユーザーに質問して解消する。資料間の矛盾（要件定義書と Figma で画面構成が食い違うなど）もここで扱う。質問は一度に全部ではなく、重要な順に数件ずつ、「なぜその情報が要るか」を添えて聞く。

カレントリポジトリに実装コードが存在する場合は、既存システムへの機能追加か新規システムかをここで確認する。

### 2. 既存コードベースの調査

フェーズ1で既存システムへの追加と確認された場合は、設計の前にコードベースを調査する。見るのはアーキテクチャ（レイヤ構成・ディレクトリ構造）、命名規則、技術選定（フレームワーク・ライブラリ・DB）、それに今回の要件と似た既存機能の実装パターン。既存の構造を無視した設計書は実装で使い物にならないため、この調査は省略しない。調査で要件との矛盾（既存データモデルと相容れない要件など）が見つかったら、フェーズ1の質問に戻る。

### 3. 主要な設計判断の承認

アーキテクチャ方式やデータモデルの大枠など、複数の妥当な選択肢がある判断について、選択肢とトレードオフ、推奨案を提示してユーザーの承認を得る。件数は2〜5件程度を目安とし、超える場合は影響の大きい順に提示する。セクションの省略提案（該当しない場合）もここに含める。

方式選定を誤ると設計書全体の書き直しになり、最も手戻りが大きい。だからここだけは執筆前にユーザーと固める。

### 4. 設計書の執筆

承認された方針に基づき、`references/templates.md` のテンプレートに従って各ファイルを書く（Figma で与えられたデザインの扱いも同ファイルの 04-ui の注記に従う）。承認済みの設計判断と質疑応答の記録は、`00-overview.md` の設計判断サマリに必ず残す。この記録は次フェーズのレビュアーが「創作かどうか」を判定する根拠になるため、省くとレビューが成立しない。

### 5. サブエージェントレビュー

文脈を持たないサブエージェントに、次の3点だけを渡してレビューさせる。会話の経緯は渡さない。

- 要件・仕様資料のパス（Figma は URL）
- 設計書のパス（`00-overview.md` の設計判断サマリを含む）
- レビュアー指示書 `references/review.md` のパスと、担当する役割

レビュー観点は、要件のカバー漏れ、セクション間の矛盾、創作の混入の3つ。定義と検証方法は指示書側にある。

レビュー体制は設計書の規模で切り替える。

- **一括レビュー（既定）**。レビュアー1体に設計書一式を渡し、3観点すべてを担当させる。
- **2層レビュー**。「規模に応じた分割」が発生した場合、または設計書一式が明らかに1体のコンテキストに収まらない場合はこちら。巨大な一式を1体で読むと横断検証の精度から先に落ちるため、役割を分ける。
  - ファイル担当レビュアー（並列可）：セクションファイル（分割時は分割ファイル）ごとに1体。創作の混入と、要件対応表でそのファイルへ割り当てられた要件が実際に書かれているかを検証する。設計書は `00-overview.md` と担当ファイルだけを渡す。
  - 横断レビュアー（1体）：設計書一式を渡し、カバー漏れとセクション間の矛盾を専任で検証させる。

修正ループは重大指摘がゼロになるまで、**最大3回**。2層レビューの再実行は、修正したファイルの担当レビュアーと横断レビュアーだけでよい。上限に達したら残った指摘を最終報告に記載してユーザーの判断に委ねる。書いた本人（同一コンテキスト）のセルフチェックでは自分の思い込みを検出できないため、このレビューを省略してはならない。

### 6. 仕上げ

対象リポジトリに lint 設定（markdownlint、textlint、prettier など）があれば設計書に実行して整形する。自動修正で解消しないものは可能な限り手動修正し、残りは最終報告に含める。lint 設定がないリポジトリでは何もしなくてよい。

最後に、生成したファイル一覧、承認済み設計判断の要約、レビューの結果（残指摘があればそれも）をユーザーに報告する。

## 改定モード（差分更新）

出力先にこのスキルの設計書一式が既に存在し、要件の改訂を反映する場合はこちらで進める。全再生成は承認済みの設計判断・質疑応答・改訂履歴という蓄積を捨てることになるため、ユーザーが明示的に求めた場合に限る。なお、要件の変更を伴わない軽微な修正依頼（誤記・表現の調整）はこのモードを通さず通常の編集で応じてよい。ただし、設計内容に関わる修正であれば改訂履歴へ1行追記する。

次の5フェーズで進める。初版と同じく、フェーズ3の承認より前に本文を書き換えない。

### 1. 既存設計書の把握

`00-overview.md` を起点に設計書一式を読み、要件 ID・設計判断（D-xx）・質疑応答（Q-xx）・改訂履歴の現状を把握する。要件対応表が既存要件のベースラインとなり、次フェーズの差分特定はこれとの突き合わせで行う。

### 2. 差分の特定

改訂後の資料を初版フェーズ1と同じ要領で読解・項目化し、要件対応表と突き合わせて要件を「追加・変更・削除」に分類する。既存の要件 ID は据え置く。追加分は、改訂後の資料に採番があればそれを使い、なければ仮 ID の連番の続きで採番する。変更と見なすべきか判断がつかない項目は、推測で分類せずユーザーに確認する。改訂部分の不足・矛盾に対する質問も、初版と同じ要領でこのフェーズ内に行う。既存コードベースの調査（初版フェーズ2）は、変更が既存実装に関わる場合のみ該当箇所に絞って行う。

### 3. 影響分析の承認

差分ごとに、影響を受ける設計書のファイル・セクションと、見直しが必要になる承認済み判断（D-xx）を一覧で提示し、更新方針の承認を得る。影響が及ばないセクションには手を入れないことも、ここで合意する。差分が広範囲に及び影響分析が意味をなさない場合（アーキテクチャ方式の変更など）は、全再生成への切り替えを提案してよい。

### 4. 差分の反映

承認された影響範囲のセクションだけを更新する。影響範囲外の「ついで修正」はしない（変更の追跡が壊れ、レビューでも差分と無関係な指摘が混ざるため）。合わせて `00-overview.md` の要件対応表・設計判断サマリ・質疑応答の記録・改訂履歴を更新する。廃止要件の残し方や版の進め方などの細目は `references/templates.md` に従う。

### 5. レビューと仕上げ

初版フェーズ5・6と同じ手順で行う。レビューは変更ファイルだけでなく設計書一式を対象にする。部分更新はセクション間の食い違い（更新漏れで残った古い記述）を最も生みやすく、それは全体を突き合わせないと検出できないため。レビュアーには改訂後の要件資料を渡す。最終報告には今回の改訂履歴エントリ（版・変更要約・更新ファイル）を含める。

## やらないこと

- **詳細設計・実装**。クラス設計やコードは書かない。実装は設計書を受け取ったエージェントの仕事。
- **要件定義書の改訂**。要件側の不備は質問や最終報告で指摘するに留め、勝手に書き換えない。
- **黙っての全再生成**。既存の設計書がある場合の再実行は改定モードが既定で、全再生成はユーザーの明示指示があるときに限る。
